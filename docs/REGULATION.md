# Регламент команды Synapse

Версия 1.0 · 2026-11-02 · владелец: Мастер · хранитель: Warden.
Эта страница — источник правил для всех ролей. Её URL задаётся в профиле ScriptCat и
показывается ролям в каждом ходе. Репозиторная копия: `docs/REGULATION.md` в `synapse-cortex`.

## 1. Проект и границы

Synapse — AI-friendly конструктор игр на Godot 4.7.2. Два продукта: **система создания игр**
(локальная, MIT) и **платформа мастерской** (проприетарная). Локальная игра собирается и
запускается без аккаунта, платформы и сети.

| Репозиторий | Лицензия | Кто пишет | Что это |
|---|---|---|---|
| `Creative36711/synapse` | MIT | агент с доступом к нему | ядро, CLI, редактор, GameSpec, модули, рецепты, инструменты агентов |
| `Creative36711/synapse-cortex` | проприетарная | Warden и агенты cortex | транспорт ScriptCat, backend мастерской, платформа, коммерческая часть |

Инвариант №1: **всё нужное для локальной сборки и экспорта игры лежит в `synapse` под MIT.**
Если агенту требуется закрытый компонент, чтобы собрать игру — это дефект архитектуры.

Дорожная карта и фазы ведутся в `docs/PHASE0.md` + `docs/DECISIONS.md` (cortex). Активна
ровно одна фаза. Реализуется только текущая фаза и минимальные границы следующей.

## 2. Роли

| Участник | Делает | Не делает |
|---|---|---|
| **Мастер** | направление, целевые рамки, доступы, лицензии и деньги, финальные решения по ADR | не подменяет приёмку пустым подтверждением, не публикует секреты |
| **Warden** (`Функция = Reviewer`) | пишет ТЗ миссий, принимает миссию по оракулу, отвечает на вопросы и ADR | не пишет код карточек, не правит очередь и «Итог», не подменяет Coordinator |
| **Coordinator** (`Функция = Coordinator`) | разбирает очередь `Draft → Ready`, нарезает карточки, выдаёт ходы, разбирает `Submitted`, ведёт «Итог» | не пишет код и PR, не выдаёт Reviewer рабочие карточки, не закрывает миссию |
| **Executor** (`Функция = Executor`) | выполняет карточку в своём `Scope`, держит инварианты, выполняет оракул, сдаёт отчёт с доказательствами | не выходит за `Scope`, не ослабляет проверки, не объявляет merge без факта |
| **Auditor** (`Функция = Auditor`) | независимо проверяет результат, запускает разрешённые проверки, сообщает находки | не исправляет проверяемый код |

Один проект — одна активная вкладка ScriptCat. Имя роли в «Ролях» — ровно то же, что опция
`Кому` в «Запросах». Reviewer не получает обычных рабочих карточек.

## 3. Зоны записи и гейты

Зоны определяются репозиторием, а не человеком:

| Зона | Кто пишет | Гейт |
|---|---|---|
| `synapse/**` | Executor, у которого есть доступ к `synapse` | PR в `main`; merge только после зелёного оракула карточки |
| `synapse-cortex/**` | Warden; Executor cortex — по `Scope` карточки | PR в `main` cortex; merge после приёмки Warden |
| `tools/script-cat/**` | никто без отдельной карточки | транспорт не переписывается под проект: настройка идёт профилем |
| Notion: базы проекта | Coordinator (очередь, статусы), транспорт (состояния, Run ID) | «Роли» и решения ADR правит только владелец процесса |
| Drive `Arena/synapse/{logs,payloads}` | только Drive Gateway | руками не правится |
| `docs/decisions/**` | Executor по `Scope` карточки | запись предложения — не решение; `accepted` оформляет исполнитель после фактического ответа |

Секреты (токены Notion/GitHub, ключ шлюза, реестр шлюза, пароли) не попадают в чат, логи,
документы, Git и PR. Агент их не запрашивает и не выводит.

## 4. Оракул: обязательные проверки проекта

Зона оракула защищена: тесты, фикстуры, эталоны и контрольные суммы можно дополнять, но нельзя
удалять, ослаблять или подгонять под код.

**Cortex (этот репозиторий), из корня:**

```bash
npm run scriptcat:check      # relay.user.js соответствует src/
npm run scriptcat:guard      # переносимый комплект чист от имени прежнего проекта
npm test                     # 72 smoke-пробы транспорта
npm run test:regression      # 14 интеграционных проб, включая схему Notion из фикстуры
npm run verify               # всё подряд; успех = код 0 и «# fail 0»
```

**Ядро (`synapse`), из корня:**

```bash
tools/godot/install.sh --check                 # установка Godot 4.7.2 + smoke-рендер
tools/media/setup.sh --check                   # venv медиа-инструментов + self-test
tools/modeling/setup_bpy.sh --check            # Blender/bpy + self-test
```

Для игровых проверок используется `tools/godot/agent_bridge` (скриншоты и ввод), для визуальных
критериев агент обязан **сам открыть полученные PNG** и описать наблюдаемое.

Отдельно фиксируется: длительные проверки, единый финальный SHA миссии, независимый аудит —
если ТЗ миссии этого требует. `not run`, тайм-аут, работающий CI и мок не равны pass.

## 5. Цикл и маркеры

1. Мастер/Warden готовит ТЗ миссии → строка в «Миссиях» (`Черновик`, позже `Активна`).
2. Coordinator превращает `Draft` в `Ready`, выбирает по `Sequence`, выдаёт ход.
3. Транспорт пишет лог попытки в Drive и переводит карточку `Running → Submitted`.
4. Executor завершает отчёт маркером `CF_AGENT_RESULT` с реальными `dispatch_id`/`run_id`,
   `pr: null` при работе без PR; `merged: true` — только после фактического merge.
5. Coordinator проверяет `Acceptance`: `Accepted` или `Rework` с конкретной причиной.
   `Accepted` — обработка карточки, не закрытие миссии.
6. Готов результат → `next: "done"` — это передача Warden.
7. Warden проверяет миссию по оракулу: `accept` / `rework` / `master`.
8. `master` — только когда без Мастера физически невозможно продолжить (доступ, аккаунт,
   браузер, деньги, юридическое решение).

Маркер не заменяет отчёт. Зелёная карточка не заменяет финальный оракул миссии.

## 6. Вопросы, предложения и ADR

Обратимое решение внутри полномочий принимается самостоятельно и оставляет след
«неясно / решил / откат» в разрешённом журнале.

Изменение контракта, оракула или границ продукта — **предложение**, а не решение: поле `question`
с текстом, начинающимся `ADR:`, контекстом, последствиями, тремя вариантами,
`default: "оставить как есть"` и сроком. Дефолт и истечение срока решением не являются.
Оставшийся без ответа ADR — видимый долг, который блокирует связанные карточки.

Что требует Мастера, а не Warden: лицензии и ToS, деньги и комиссии, платные серверы,
исполнение пользовательского кода на платформе, целевая аудитория, доступы и аккаунты.

## 7. Запреты фаз 0–4

- Не строить подключение к платежам, каталог, загрузку пакетов, аккаунты — до своих фаз.
- Не запускать пользовательский код на платформе и не считать манифест разрешений песочницей.
- Не обещать авторам долю от будущей монетизации и не запрещать продажи вне платформы.
- Не вводить виртуальную валюту, комиссию с внешних транзакций, ограничения на экспорт игр.
- Не разворачивать платную инфраструктуру без согласованного лимита (`docs/COST_MODEL.md`).
- Не называть ядро open source, если его лицензия не одобрена OSI.
- Не создавать пустые сервисы «под будущие фазы».
