## D-045 (1.12.10): записи хода доживают до перехода, потерянное ожидание восстанавливается сверкой
Боевой SYN-1 · K-27 «Проверка CLI-контракта»: 09:36:54 «Выдан ход», журнал выдачи создан
(06:36:46.179Z), вкладка ушла на страницу Executor Core — а в 09:37:12 цикл встал на
`delivery-state-lost` (сообщение `01a1af93-3a0c-79ea-b456-263d4d41def7`). В 06:40:49Z агент
уже ответил полным отчётом с `CF_AGENT_RESULT`; ответ не был принят.

**Причина.** `GM_setValue` в ScriptCat синхронен только наполовину: значение кладётся в
память вкладки, а запись в базу уходит сообщением service worker'у без ожидания.
`location.assign` сразу за пачкой записей обрезает её хвост. На K-27 пропали `K.expect`,
журнал промптов и строка журнала, а `K.pending` уцелел: очередь без ожидания отправила
задание и обнаружила, что хозяина хода нет.

**Что изменилось.**
1. `flushBeforeNavigate(keys, ms)` перезаписывает ключи хода через `GM.setValue` и ждёт
   подтверждения не дольше 4 с (`Promise.race`): подтверждение может не прийти вовсе, и
   зависнуть хуже, чем уйти. Отсутствующие ключи не создаются, отказ не бросается наружу,
   менеджер без `GM.setValue` получает короткую паузу. Барьер стоит перед каждым уходом со
   страницы: `sendToRole`, `navigateTo`, обе перезагрузки и пилот.
2. `sendToRole` пишет ожидание **до** очереди: при усечении теряется очередь, а не хозяин
   хода. Очередь несёт плоские опознавательные поля выдачи (ref/runId/missionId/logId/…).
3. `adoptOrphanDispatch` разбирает очередь без ожидания **до разбора просрочки** и до
   отправки (иначе залежавшийся K-27 снимался бы как остаток прошлой попытки): сверка карточки
   (Running, Run ID, Recipient, Mission ID) → квитанция или реплика в чате → снять очередь
   и читать ответ, либо восстановить ожидание и отправить ровно один раз. Расхождение или
   недоступный Notion — пауза `orphan-dispatch` без отправки и без изменения карточки.
4. Разбор dispatch/run общий для ключа доставки и поиска реплики. Прежний скобочный
   regexp не встречался в боевом промпте вовсе: восстановление по чату было мертво.
5. Квитанция доставки пишется и в ветке `delivery-state-lost` — до паузы. «Продолжить»
   больше не обещает повторную отправку подтверждённого сообщения.

**Проверка.** Новая регрессия `relay-handoff-flush-integration` на **настоящем промпте
боевого компилятора**: ключ доставки — подстрока сообщения и меняется с новым Run;
барьер ждёт подтверждение, ограничен таймаутом, не создаёт лишних ключей и не бросается;
порядок «ожидание → очередь → подтверждение → переход»; восстановленный ход не отправляется
вторично; пять видов расхождения с карточкой и отказ Notion дают паузу без побочных эффектов.
Обвязки `pilot-smoke`, `relay-auto-run-smoke`, `relay-page-ready-smoke`,
`relay-delivery-receipt-smoke`, `relay-reviewer-task-guard-integration` обновлены под новые
вызовы без ослабления проверок. Прогоны: `verify` — **107 smoke / 22 regression / 2 tool-limit,
exit 0**; `test:provision` — **28/28**.

**Не менялось.** Бюджеты промптов, оракул, Scope, маркеры, профили и блоки; Gateway 1.8.0;
digest/REGULATION 1.5; protocolVersion 1.10 (аддитивная секция `d045`). Живая карточка K-27
из песочницы не переводилась в Running вручную.

- **Проверки:** `relay-delivery-receipt-smoke` (новая), обновлённые `relay-step-smoke`,

  `docs-smoke` OK. Контракт `agent-protocol.json`: аддитивная секция `d044`, protocolVersion
  **1.10** не менялся; бюджеты не поднимались, оракул/Scope/инварианты не обрезались.
- **Живая карточка K-30 из песочницы не правилась.** После обновления Мастер сверяет чат,

## D-043 (1.12.8): бюджет выдачи проверяется до Running; причина отказа доходит Координатору
Боевой SYN-1 · K-29 «Вендоринг CJK-шрифтов Noto Sans JP/KR/SC и fallback-стек темы
(D-016, вариант C)»: после решения Warden Координатор выбрал K-29 → Executor Core.
В 22:24:30 промпт не собрался: **total 10381 > жёсткого лимита 7500**. Карточка откатилась
в Ready, в 22:24:43 запрошен новый план, дальше цикл стоял на паузе. Отдельного payload у
K-29 нет; по Drive-журналу оракул — **4232** знака, Scope — **1435**, инварианты — **1035**,
намерение — **626**. Payload-канал выносит только прикреплённое тело задания, а
оракул/Scope/инварианты остаются inline; compact для dispatch не уменьшает полный профиль.
**Это не ошибка Warden и не сетевой сбой.** Дефект транспорта: Running/журнал создавались
до сборки промпта, null ошибочно назывался «дублем», а диагностика показывала overhead
marker/git вместо контентных блоков. Что сделано:

- **Проверка до журнала и Running:** снимок payload (если есть) и промпт собираются до
  createLog и patch `Dispatch State=Running`; `sendToRole` получает уже проверенный текст.
  Отказ сборки возвращает карточку без смены статуса, без отправки агенту и без создания
  журнала выдачи. Поздний fail-closed guard компилятора сохранён запасным путём.
- **Исполнимая причина Координатору:** отказ идёт строкой в `requestPlan` → `plan.note`
  (D-042): убрать повторы/справочные детали, при необходимости разбить работу на
  последовательные карточки с полными условиями и Dependency, не ослаблять/не обрезать
  оракул; `Payload Drive File ID` не заменяет inline-оракул/Scope. Затем повторить `next`.
- **Ограниченные попытки:** `cfn-dispatch-miss` сбрасывается только после успешной сборки;
  третий подряд отказ ставит штатную паузу. Сообщение паузы/заметки больше не сводит любую
  причину к «поправь состояние». Ложное «то же сообщение уже уходило» убрано.
- **Диагностика total:** `budgetBreakdownLine` при total показывает топ-4 по `chars`
  fact-блоков (`task.acceptance`, `task.scope`, `task.invariants`, `task.intent`), а не
  нулевой overhead; overhead-диагностика D-034 сохранена.
- **Бюджеты не подняты, требования не обрезаны.** Executor остаётся ≤7500, Auditor ≤5500,
  Reviewer ≤7000; оракул/Scope/инварианты verbatim. Gateway 1.8.0 и digest 1.5 не менялись.
- **Контракт:** protocolVersion остаётся **1.10** (транспорт-внутренний фикс, аддитивная
  секция `d043`); ScriptCat **1.12.8**.
- **Регрессия:** новая `relay-dispatch-budget-preflight-integration` на дословной фикстуре
  K-29 (`fixtures/k29-card.json`): ранний отказ до журнала/Running/отправки/паузы; причина с
  размерами блоков и подсказкой; счётчик не сброшен; два возврата через `plan.note`, третий —
  пауза `redispatch`; успешная выдача сбрасывает счётчик; поздний guard и лимит 7500 сохранены.
  `relay-payload-smoke`, `relay-payload-channel-integration`, `relay-reviewer-task-guard-integration`,
  `relay-coordinator-note-delivery-integration` — зелёные.

## D-041 (1.12.6): запасной fetch с таймаутом — выдача не зависает посреди Running
Боевой SYN-1: Координатор ответил маркером «дальше Contract Architect» (18:49:09),
выдача поставила карточку в Running, но затем `gateway("append")` **завис на

`fetch` в `gatewayWithCredentials` и ntfy шёл без `AbortController`/таймаута и мог
висеть вечно. Сетевой запрос не отмечает жизнь (`busyAt`), поэтому сторож (120 с)
срабатывал и перезапускал шаг посреди выдачи. Что сделано:

- **`fetchWithTimeout(url, opts, ms)`** в `03-utils.js`: `fetch` + `AbortController`
  с таймаутом, таймер очищается после завершения. Отметку жизни не ставит (это
  сетевой запрос, а не честная пауза).
- **Применён во всех трёх запасных fetch** по таймауту их GM-путей:
  `gatewayWithCredentials` — **45 с**, `ntfyPublish` — **15 с**, `ntfyHealth` — **15 с**.
- **Отказ стал явным и ловимым:** `gateway("append")` в `dispatchTask` обёрнут в
  `try/catch` — незаписанный журнал попытки логируется («Задание не записалось в
  журнал попытки»), выдача продолжается (карточка Running, промпт уходит агенту),
  а не зависает навсегда. Сторож больше не перезапускает выдачу посреди Running.
- **Агентский контракт не менялся** — protocolVersion остаётся **1.9**; фикс
  транспорт-внутренний. Бюджеты промптов не подняты.
- **Регрессия:** новая `relay-fetch-timeout-integration` — зависший fetch обрывается
  по таймауту и не висит; успешный ответ возвращается; пины таймаутов шлюз 45 с /
  ntfy 15 с; в шлюзе и ntfy нет fetch без таймаута; `gateway("append")` ловится
  `try/catch`. Harness `relay-gateway-path-smoke`, `relay-ntfy-transport-smoke`,
  `scriptcat-gateway-smoke` переведены на `fetchWithTimeout` (pass-through к моку
  fetch) — логика путей GM-then-fetch и идемпотентный append сохранены.

Прогоны: `verify` — **106 smoke / 19 regression / 2 tool-limit, exit 0**;
`test:provision` — **28/28**; `docs-smoke` OK (protocolVersion 1.9). Тесты не
ослаблялись. Gateway и digest не менялись.

## D-040 (1.12.5): маркер без dispatch_id/run_id — напоминание с точными ID, а не сразу пауза
После D-039 доставка K-21 **прошла** (17:21:18, 6642 зн.), Executor Core реально
выполнил работу и слил PR Creative36711/synapse#8. Но в 17:30:21 цикл встал: «Ответ
не подтверждён для текущей карточки и попытки (dispatch_id / run_id)». **Виновник —
агент:** финальный маркер пришёл как `CF_AGENT_RESULT: {"task":"K-21",…,"merged":true,
"pr":…}` — с двоеточием, с `task` вместо `dispatch_id`/`run_id` и без `status`.
Транспорт **верно отказал** в подтверждении (защита от зачёта чужой/прошлой попытки),
но ветка mismatch сразу ушла в паузу, минуя лестницу напоминаний: работа сделана, а
цикл требует ручного вмешательства. Что сделано:

- **`dispatchIdState(result, expect)`** различает `match` / `missing` / `conflict`.
  `missing` (ни один присутствующий ID не противоречит выдаче, но ID не хватает) —
  формат-дефект, а не чужой ответ.
- **`missing` → напоминание** через существующую лестницу `markerMissing(…, why="ids")`
  (до `markerReminders=2` раз). Блок `reminder.marker` с `why=ids` просит повторить
  **только маркер** с точными `dispatch_id`/`run_id` из напоминания, работу не
  переделывать. Копия ответа сохраняется локально до классификации.
- **`conflict` (чужие/битые/противоречащие ID) → прежняя сразу-пауза**

## Инструкция Мастеру
1. Обновить ScriptCat до 1.10.0; развернуть Gateway 1.8.0 тем же ключом (папки и
   история сохраняются). Автоцикл остановить.
2. В профиле включить provisioning, задать allowlist точных `owner/repo`, bootstrap-пробник,
   лимиты, режим manual. В Notion добавить аддитивные поля и отметить `Agent Admin=true`
   у действующего Coordinator/Reviewer.
3. Создать тестовую роль: `Agent State=запрошен`, пустой Agent URL, repo из allowlist.
   Нажать «🤖 Агенты» → запрос → одобрение маркером. Проверить URL/rename/Активна/Кому.
4. Заменить временную роль: заполнить URL, `Agent State=запрошен`; проверить Previous Agent URL
   и архив старого. Негативные: чужой request_id, repo вне allowlist, админ-кандидат, conflict.
5. Откат: выключить provisioning, снять `Agent State`, вернуть прежний URL/Статус вручную;
   старый URL при replace хранится в `Previous Agent URL`. Новая сессия при захваченном URL
   повторно не создаётся.
