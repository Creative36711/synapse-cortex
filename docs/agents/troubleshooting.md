# Диагностика отказов доставки

| Класс | Признак | Действие скрипта | Что делает Мастер |
|---|---|---|---|
| editor_not_found | поле ввода не найдено | повтор до лимита, затем пауза | обновить страницу, «Продолжить» |
| send_disabled | кнопка Send неактивна | пауза | проверить страницу |
| captcha | Security Verification | пауза, очередь сохранена | решить капчу, «Продолжить» |
| auth / agent_unavailable | 401 / агент недоступен | пауза | проверить доступ/URL роли |
| tool_call_limit | «reached the tool-call limit for this turn» | короткое продолжение того же хода (до 2), затем пауза | см. карточку ниже |
| rate_limit | 429 / too many requests | пауза | подождать, «Продолжить» |
| arena_generic_error | Something went wrong | один компактный повтор того же хода | если повтор не помог — пауза |
| network | failed to fetch / timeout | пауза | проверить сеть |
| budget_exceeded | промпт не влезает в лимит | пауза, оракул не режется | уменьшить payload/карточку |
| delivery-state-lost | сообщение в чате подтверждено, а ожидание потеряно/подменено | пауза, очередь сохранена, автоповтора нет | сверить чат, карточку и Run ID; ↺ или ручное продолжение |
| unknown | прочее | пауза с текстом ошибки | разобрать по журналу |

## Журнал попытки
Кольцо `cfn-prompt-journal-v1` (200 записей): профиль, блоки+версии+хеши,
метрики (chars/utf8Bytes/lines/overhead), попытка, исход, класс ошибки.
Смотреть через консоль ScriptCat; секретов в журнале нет.

## «Задание не дошло: отметки отправки нет», хотя ответ есть (D-044)
- **Симптом.** В журнале есть «Задание отправлено (… сообщение `<id>`)», агент ответил
  с маркером этой выдачи, но карточка возвращена в Ready со словами «отметки отправки нет».
- **Причина.** Прежняя уборка фантомов верила только `expect.sentAt`. Если запись ожидания
  позднее теряла отметку, готовый ответ становился невидим. Это ошибка транспорта, не агента.
- **Что делает 1.12.10 (и 1.12.9).** Квитанция доставки пишется отдельно до снятия очереди; перед откатом
  отметка восстанавливается по квитанции или по реплике с точными dispatch/run ID в чате
  адресата. Доказанная доставка не откатывается. Настоящий фантом без доказательств снимается.
- **Что делает Мастер.** Обновиться до 1.12.10, оставить одну вкладку, сверить чат/карточку/журнал.
  Если карточка уже ложно возвращена в Ready, не выдавать повтор вслепую: готовый ответ и
  ADR-вопрос нужно провести через приёмку. Пауза `delivery-state-lost` требует сверки, а не
  автоматического повтора.

## Пауза «Сообщение подтверждено в чате, но ожидание выдачи потеряно» (D-045)
- **Симптом.** Пауза `delivery-state-lost` сразу после «Выдан ход», хотя агент уже ответил.
- **Причина.** Запись ожидания не дожила до перехода на страницу адресата: `GM_setValue`
  пишет в базу асинхронно, а уход со страницы обрывал хвост пачки. Очередь уцелела и
  отправила задание без хозяина хода.
- **Что делает 1.12.10.** Записи хода доводятся до хранилища до перехода; ожидание пишется
  раньше очереди; очередь без ожидания сперва сверяется с карточкой и чатом и либо
  снимается (сообщение уже в чате), либо отправляется ровно один раз. Квитанция доставки
  сохраняется и при такой паузе.
- **Что делает Мастер.** Обновиться до 1.12.10 и нажать «Продолжить»: скрипт сверит чат и
  карточку сам. **На версии 1.12.9 и старше «Продолжить» отправит задание повторно** —
  сначала обновление. Расхождение с карточкой даёт паузу `orphan-dispatch`: тогда нужны
  чат, карточка и Run ID, автоматического повтора не будет.

## Два плана Координатору подряд после возврата миссии (D-047)
- **Симптом.** После возврата миссии Координатор получает план с замечаниями, отвечает
  (карточки созданы, в «Итоге» появился раздел «Возврат»), а через несколько минут ему
  уходит **второй** план. Дублей карточек при этом может не быть: агент сверяется с очередью.
- **Причина.** Снятие «устаревшего» ожидания сравнивало время отправки плана с
  `last_edited_time` карточки миссии. Координатор пишет «Итог» в том же ходе, правка карточки
  сдвигала отсчёт вперёд, и живой план выглядел как прошлый ход.
- **Что делает 1.12.12.** Сначала снимок «план отправлен уже с замечаниями», затем раздел
  «Возврат» в «Итоге», затем отметка объявления возврата; время правки карточки — последнее
  средство. Ожидание прошлого хода по-прежнему снимается.
- **Что делает Мастер.** Ничего: на 1.12.12 переспрос не повторяется. На 1.12.11 и старше
  один лишний ход безопасен, но стоит минут и лимитов — агент сверяется с очередью и правит
  существующие карточки, а не создаёт дубли.

## Пауза «в «Итоге» нет раздела «Возврат»», хотя раздел есть (D-048)
- **Симптом.** Координатор ответил «done» после возврата, в чате видны «Итог хода» и
  раздел «Возврат», а транспорт поставил паузу `done-with-remarks`.
- **Причина.** Скрипт читал только свойство «Итог», а Координатор дописал раздел
  блоками на странице миссии — в карточке миссии два места с одинаковым названием.
- **Что делает 1.12.13.** Читаются оба: сначала свойство, затем текстовые блоки
  страницы миссии (без дочерних страниц карточек). Ошибка чтения блоков цикл не
  блокирует.
- **Что делает Мастер.** На 1.12.13 — ничего. На 1.12.12 и старше: нажмите
  «Продолжить» — Координатор повторит ход; либо перенесите раздел в свойство «Итог».

## Выдача не собралась: `budget_exceeded total 7802 > 7500` (D-048)
- **Симптом.** Обычная карточка на правку в один абзац не выдаётся, ход возвращается
  Координатору с советом «разбей карточку».
- **Причина.** Оракул, Scope и инварианты не режутся (D-034/D-038), поэтому почти весь
  размер — подлинный контент задачи. Лимит 7500 не покрывал такие карточки.
- **Что делает 1.12.13.** `DISPATCH_TOTAL.Executor` 7500 → 8000. Оракул по-прежнему
  verbatim; Auditor 5500, Coordinator 7500, Reviewer 7000 не менялись.
- **Что делает Мастер.** Ничего. Если и 8000 мало — карточка дробится по существу или
  задание уходит payload-файлом; лимит вручную не поднимайте.

## Пауза «Ответ не подтверждён… (dispatch_id / run_id)» из-за одного знака (D-054)
- **Симптом.** 07.11.2026, 17:04: агент сдал работу (отчёт и PR на месте), но цикл встал
  на паузе `marker-mismatch`: «Ответ не подтверждён для текущей карточки и попытки».
  В маркере `run_id` отличался от выдачи одним символом — `…-e5db-…` вместо `…-e5d6-…`.
- **Причина.** Агент набирал UUID по памяти и повторил опечатку в нескольких ответах.
  До 1.12.15 транспорт считал такой маркер чужим, а «Продолжить» не помогало: ожидание
  хранит прежний `runId`, и тот же маркер снова давал конфликт.
- **Что делает 1.12.15.** Одна замена знака в `run_id` при верном `dispatch_id` и карточке,
  которая всё ещё несёт **ожидаемый** `Run ID` и того же владельца, считается опечаткой:
  ответ принимается, работа не повторяется, в журнал идёт строка «Run ID с опечаткой».
  Всё остальное (две замены, другой UUID, перевыданная карточка, недоступный Notion) —
  прежняя пауза.
- **Что делает Мастер.** Если пауза всё-таки пришла, сравните `Run ID` в карточке и в
  маркере: инструкция агенту — скопировать строку маркера целиком, а не печатать ID.
  Снимать паузу «Продолжить» бессмысленно: она не меняет ожидание.

## Карточку перевыдали несколько раз: петля уходит арбитру (D-053)
- **Симптом.** Одна и та же карточка снова и снова возвращается в работу: «перевыдали
  N раз за шесть часов». Например 07.11 SYN-2 · S-4: PR открыт, но помечен draft, в
  теле прямо назван scope blocker — транспорт каждый раз видел «нет заявки о мерже».
- **Причина.** Неверна постановка, а не работа транспорта: правило «нет мержа → Rework»
  верное, но круг повторяется, потому что карточка требует того, что вне её зоны.
  Раньше третья перевыдача сразу ставила паузу `redispatch` и звала Мастера.
- **Что делает 1.12.14.** Порог перевыдач уходит арбитру — роли с функцией `Reviewer`
  (Warden): вид хода `arbiter`, маркер `CF_ARBITER_RESULT`. Арбитр видит «Ответ»,
  состояние и `Check` карточки, состояние PR по GitHub, журнал попыток и очередь.
  `resolve` + `ready/rework/accepted/blocked` применяется к этой же карточке, разбор
  пишется в «Ответ», ход возвращается Координатору. `master` — цикл остановлен
  (`arbiter-master`). Без активного Reviewer или после двух разборов на карточку —
  прежняя пауза Мастера (`redispatch` / `arbiter-limit`).
- **Что делает Мастер.** На 1.12.14 — ничего: сначала разбирает Warden. Если пришла
  пауза `arbiter-master` или `arbiter-limit`, откройте «Ответ» карточки и журнал
  попыток: там причина петли и правка постановки. На 1.12.13 и старше — пауза
  `redispatch` требует ручного разбора.

## Ошибки компиляции
`missing_fact`, `forbidden_block`, `marker_mismatch`, `budget_exceeded`,
`unknown_profile` → локальная пауза ДО отправки. Исправьте факты/профиль и
нажмите «Продолжить».

## Агент достиг tool-call limit
- **Симптом.** В чате Arena amber-статус (`role=status`/`alert`): «The agent
  reached the tool-call limit for this turn. Send a message to continue where it
  left off.» Ход не завершён маркером, агент остановился на середине работы.
- **Причина.** Arena ограничивает число вызовов инструментов за один ход. Это не
  отказ доставки исходного промпта, не captcha/auth/rate лимит аккаунта и не
  «агент забыл маркер». Часть работы уже могла быть сделана.
- **Что проверить.** Что страница — того агента, которого ждём (`K.expect`); что
  доставка исходного хода подтверждена или ход начался; что агент не генерирует
  (нет Stop); что маркера этой выдачи ещё нет в чате; что статус не в
  pre/code/diff/редакторе; счётчик `toolLimitContinuations` и `lastToolLimitMessageId`.
- **Безопасное действие.** Скрипт сам шлёт короткое continuation-сообщение
  (`continuation.*`, overhead ≤700) в тот же чат: «продолжи с того места, не
  начинай сначала, IDs прежние, маркер после завершения». До 2 продолжений
  (`toolLimitContinueMax`). Исходные dispatch/run, mission/turn, question/turn IDs,
  карточка Notion, PR и терминальные поля не меняются; новый Run ID не создаётся.
  Исходный watermark сохраняется, поэтому финальный журнал собирает части до лимита
  и отчёт после.
- **Когда звать Мастера.** Лимит достигнут снова после 2 продолжений; после
  продолжения нет новых содержательных сообщений (только повторный лимит);
  продолжение не удалось отправить; страница/роль не совпадает; tool-limit на
  рабочей карточке Reviewer (продолжение не шаблонизировано). Во всех этих случаях
  скрипт ставит паузу и НЕ откатывает карточку. Мастер проверяет страницу агента и
  решает: «Продолжить» вручную или завершить ход.
- **Чего НЕ делать.** Не отправлять исходное задание заново, не слать compact-retry
  как при недоставленном, не напоминать о маркере как при забытом, не считать это
  `budget_exceeded` только по слову «limit».

## Provisioning Arena-агентов (1.10.0)
- `provision-no-admin`: нет активной роли с `Agent Admin=true` (Coordinator/Reviewer). Мастер создаёт/включает админ-роль вручную.
- `provision_repo_trigger_ambiguous` / `provision_repo_option_missing`: repo picker неоднозначен или repo не найден. Проверьте allowlist и поле «Репозиторий»; скрипт не кликает «Add repositories».
- URL не появился за `agentUrlWaitMs`: пауза. Новая сессия повторно не создаётся, если URL уже захвачен.
- `tool-call limit` на bootstrap: пауза (continuation для provisioning в v1 нет).
- Rename failed: URL сохранён, новой сессии нет; проверьте sidebar и имя роли (≤100).
- `provision-conflict`: Agent URL/Статус изменены другим процессом; скрипт не перезаписывает.
- Автоактивация заблокирована: URL записан, `Agent State=создан`, Статус остаётся прежним. Причины: второй Coordinator, нет активного Reviewer, имя sidebar не совпадает, repo изменился, активная работа, не удалось добавить «Кому».
- `provision_old_archive_unverified`: замена успешна, архив старого не подтверждён — проверьте старый чат вручную; отката нет.
- Суточный лимит (`agentProvisionDailyMax`) или активный командный ход: запрос не выдаётся.
