## Причина (в пределах доказанного)

Разделяю доказанное и гипотезу, чтобы не повторять ошибку с «токен недоступен».

**Доказано:**
1. Терминальное состояние карточки не записалось: `Submitted At` и `PR` пусты при том, что отчёт в
   Drive создан в 11:41, а PR смержен в 11:40. Запись в Notion и работа в GitHub разошлись.
2. Повторная выдача произошла **после** успешного мержа — то есть отсутствовало хотя бы одно из двух
   условий: «не выдавать карточку, у которой есть смерженный PR» и «не выдавать карточку с
   незавершённой записью состояния».
3. Причина повтора названа самим транспортом: маркер `check=1`. Значит `Check` брался не из
   состояния карточки и не из факта мержа, а из разбора маркера в отчёте.
4. Задание повторного прогона — «доработка отчётных доказательств», а не новая работа: это шаблон
   повторной выдачи по `Check=fail`, а не санкционированный `Rework`.
5. Та же схема ранее наблюдалась на K-3: три возврата подряд, каждый — новый прогон, каждый —
   с `Check=fail`, при том что часть проверок была зелёной. Это не единичный сбой, а цикл.

**Гипотеза, требующая лога транспорта (её и надо закрыть разработчику):** `check` в маркере
нормализуется так, что отсутствующее/нечисловое значение даёт `fail`; либо маркер ищется в
нескольких местах и берётся первое найденное. Обе ветки дают одно и то же: `fail` без отрицательного
доказательства и новый прогон. Точный ответ даёт только разбор парсера и сырой лог.

## Что должен сделать транспорт (батч, окно паузы — D-027)

1. **Терминальная запись одной транзакцией.** `Submitted` + `Check` + `PR` + `Submitted At` +
   `Run ID` пишутся одним обновлением **до** любой следующей выдачи. Пока запись не подтверждена —
   повторная выдача запрещена.
2. **Неизвестное ≠ fail.** Если маркер не найден, не разобран или `check` отсутствует — `Check=none`
   и `Dispatch State=Blocked` с причиной «маркер не разобран». `fail` ставится только по явному
   отрицательному результату.
3. **Замок по факту.** Карточка, у которой есть смерженный PR или `Check=pass`, повторно не
   выдаётся ни при каких условиях; для повторной работы нужен явный `Rework` от Coordinator или
   Warden.
4. **Лимит повторов.** Не более двух автоматических повторов на карточку; третий — `Blocked` с
   причиной и записью «требуется решение Warden». Для K-3 лимит уже исчерпан.
5. **Журнал решения.** Каждая выдача пишет строку: почему выдано (первичная / повтор по `Check=fail`
   / `Rework`), какой маркер и какое условие сработали. Без этого «почему повторилось» не
   восстанавливается.
6. **Сверка при старте.** После паузы, перезапуска браузера или потери сессии транспорт сверяет
   свою последнюю выдачу с логом в Drive (последний `CF_AGENT_RESULT` по `dispatch_id`) и приводит
   `Check`/`Dispatch State` к найденному факту, а не к «по умолчанию fail».
7. **Своя ошибка называется своей.** Сообщение «токен GitHub недоступен» при ошибке парсинга —
   запрещено (исправлено в 1.8.5; правило записать, чтобы не вернулось): транспорт показывает сырой
   маркер, строку и ошибку разбора.
