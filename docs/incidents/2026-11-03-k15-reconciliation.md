## Причина: найдена по журналу транспорта

Мастер прислал журнал работы транспорта за 11:31–15:51 — это и был недостающий лог. Причина не в
маркере и не в токене как таковом, а в том, **как транспорт определяет репозиторий карточки и чем
подтверждает merge**. Цепочка целиком:

1. **PR ищется не в том репозитории, и совпадение номера принимается за подтверждение.**
   Журнал 12:07:33: «Ответ Contract Architect записан, PR слит, задача → Submitted. PR:
   `synapse-cortex/pull/2`». Карточка K-2 — карточка ядра, PR по ней живёт в `synapse`. Проверка:
   - `synapse-cortex` PR #2 — «Шлюз: детальная инструкция с прямыми ссылками», MERGED
     **2026-11-02T13:35:11Z** — за сутки до события и по другой теме;
   - настоящий PR по K-2 — `synapse` #2 «SYN-1 · K-2 · Контракты GameSpec…», MERGED
     2026-11-03T09:06:09Z.
   Транспорт взял номер `2`, посмотрел его в `synapse-cortex`, увидел `MERGED` и записал «PR слит».
   Идентичность PR (репозиторий, ветка, задача) не проверялась — проверялся только номер.
2. **То же на K-3.** Записан `synapse-cortex/pull/3` = «Supabase: состояние проекта…», MERGED
   2026-11-02T14:05:19Z. Настоящий PR — `synapse` #3, MERGED 2026-11-03T10:16:44Z.
3. **Дальше срабатывает проверка ответа и обнуляет терминальное состояние.** Журнал 12:42:56,
   13:20:53, 13:30:30, 14:34:31, 15:45:51: «проверка ответа не прошла (Check=fail): снял
   `Submitted At`, `PR` и `Run ID`, выдаю заново». Ложный merge рассыпается, но транспорт не
   различает «не подтвердилось» и «провалилось» — и очищает поля, после чего карточка снова
   выглядит невыданной. Это и есть двигатель повторов: K-2 три раза, K-3 три раза, K-15 четыре.
4. **Когда репозиторий определился верно, включается обратная ошибка — блокирующая пауза.**
   Журнал 14:42:20: «PR относится к `Creative36711/synapse`, а цель выдачи работает с
   `Creative36711/synapse-cortex`». То есть у карточки нет своего целевого репозитория: «цель
   выдачи» — это репозиторий, в котором работает сам транспорт, а не тот, где должна лежать работа.
   Правильный PR отвергается как чужой.
5. **404 не доказывает нехватку доступа.** Журнал 15:51:08 и повтор 16:46:10 сообщают 404 и для
   запроса с токеном, и для fallback. Но `Creative36711/synapse` — публичный repo, PR #5 существует
   и слит; значит фраза «может быть приватным» не является установленной причиной и не основание
   просить ещё один токен. В старой версии fallback убирал `Authorization` из заголовков, но не
   просил ScriptCat выполнить именно anonymous-запрос без browser credentials. ScriptCat 1.8.6 добавил `anonymous: true` и проверку repo endpoint. Однако журнал после обновления показал оба 404 для пути `synapse` (без owner), а не для `Creative36711/synapse`: запрос строился как `/repos/synapse/...`. Причина — свежая строка «Роли» возвращает короткий slug `synapse`, и этот raw value перекрывал полное значение из профиля. Передавать токен в чат не нужно.
6. **Побочные дефекты в том же журнале** (не причина, но чинить вместе):
   - 13:37:18 «Остановка не принята (1 из 2): роль „Warden“ активна и Agent URL заполнен — значит,
     Координатор её не увидел» — Координатор не видит адрес приёмки при попытке остановки.
   - 14:03:36 «Ответ Executor Core без маркера CF_AGENT_RESULT», в хвосте видно
     `… merged:true -->` — маркер пришёл **внутри HTML-комментария** `<!-- … -->`; разбор маркера
     обязан вытаскивать его из комментария, а не обрывать на `-->`.
   - 14:33:04 «Пока ждали план, очередь изменилась» — гонка между запросом плана и выдачей.
   - Многократные «Arena ответила Something went wrong… не принялось» при отправке длинного задания

## Что должен сделать транспорт (батч, окно паузы — D-027)

По убыванию важности; пункты 1–3 устраняют цикл, остальные — его причины.

1. **Целевой репозиторий — свойство карточки, а не окружения.** У карточки явное поле репозитория
   (или оно выводится из `Branch`/роли детерминированно), и **все** проверки — поиск PR, запись
   merge, проверка ответа — идут только по нему. `synapse-cortex` никогда не ищется для карточки ядра.
2. **Идентичность PR проверяется целиком.** Подтверждение — по URL/`headRefName`/`baseRefName` из
   GitHub, а не по номеру. Номер без репозитория и ветки — не подтверждение. Ответ GitHub «не вижу
   такой PR» отличается от «PR есть, но не смержен» и от «PR смержен, но не тот».
3. **Три состояния вместо двух.** `pass` / `fail` / `unconfirmed`. Ничего не подтверждено —
   `Check=none`, `Dispatch State=Blocked`, `Submitted At` и `Run ID` **не очищаются**, повторная
   выдача запрещена. `fail` — только по явному отрицательному результату из отчёта.
4. **Терминальная запись одной транзакцией** и запрет следующей выдачи, пока запись не подтверждена.
5. **Замок по факту.** Есть смерженный PR в целевом репозитории или `Check=pass` — повторной выдачи
   нет; только явный `Rework`.
6. **Не больше двух автоматических повторов** на карточку, третий — `Blocked` и «требуется решение
   Warden». У K-2, K-3, K-15 лимит давно исчерпан.
7. **Журнал причин выдачи** и **сверка при старте**: после паузы, перезапуска браузера и смены
   версии userscript транспорт сверяет последнюю выдачу с логом в Drive по `dispatch_id` и приводит
   `Check`/`Dispatch State` к найденному факту.
8. **Маркер разбирается из HTML-комментария**, а `-->` не считается концом маркера.
9. **Своя ошибка называется своей.** «Токену не виден репозиторий» — это сообщение об **доступе**;
   при этом оно не должно подменять «PR не подтверждён». В сообщении — репозиторий, номер, ветка,
   что именно вернул GitHub.

## Уточнение по свежему логу 1.8.6 и исправление

Пауза 17:22:08 после установки 1.8.6 не опровергает публичность `Creative36711/synapse` и не доказывает проблему анонимного режима: в тексте ошибки указан целевой repo `synapse`, без owner. При маркере с голым `pr: 5` именно он становился `ref.repo`, и скрипт вызывал `/repos/synapse/pulls/5` и затем `/repos/synapse` — оба адреса неверны. Причина в том, что `mapRoleRow` сохраняет сырое значение «Репозиторий» из Notion; короткое `synapse` перезаписывало полное значение маршрута профиля.

В ScriptCat 1.8.7 короткий slug разрешается только при единственном совпадении в allowlist профиля (`synapse` → `Creative36711/synapse`), в том числе из старого ожидания/карточки. Неоднозначный slug отклоняется до сети; неправильный `/repos/synapse` больше не отправляется. Полная ссылка PR остаётся авторитетной в рамках allowlist. `anonymous: true` остаётся точечно включённым только для запросов GitHub API без токена.

В ScriptCat 1.8.8 ситуация `Check=fail + Ready`, когда Rework не попал в снимок очереди, больше не ставит немедленную общую паузу: первый отказ возвращает Coordinator конкретную инструкцию, не меняя карточку и не переотправляя её. Coordinator-подсказка теперь требует оставить её в Rework до наблюдения транспортом; повторные отказы по-прежнему ограничены и в конце приводят к паузе.

Остальные строки лога:
- После update 1.8.6 неподтверждённый PR уже оставил карточку `Blocked`, сохранив ответ и Run ID; это ожидаемая защита от прежней петли `Check=fail → очистка → повторная выдача`.
- 14:33:04 очередь изменилась во время ожидания плана; транспорт отменил устаревшее решение и запросил новый план — безопасное поведение, а не выдача не той карточки.
- Ошибка Arena на длинной отправке запускает один минимальный повтор, затем паузу. Это ограничивает дублирование, но не устраняет внешний отказ Arena; отказ отправки сам по себе не доказывает, что агент получил задачу.
- Отклонённый `next=blocked, need=Warden` тоже не был потерей адреса: транспорт проверил, что Warden активен, вернул ход Coordinator, после чего вопрос был передан Warden штатным путём.

настроен на несколько repos, но добавление второго токена не является решением этого инцидента.
