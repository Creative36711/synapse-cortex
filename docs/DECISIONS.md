# Журнал решений

Формат записи: дата · номер · решение · причина · отклонённые альтернативы · где пересматривается.
Записи не удаляются; устаревшее помечается `deprecated` со ссылкой на замену.

## D-001 · Ядро под MIT, платформа проприетарная — 2026-11-02

**Решение.** Runtime, CLI, редактор, система модулей, валидатор, GameSpec, официальные модули и
рецепты — MIT в `synapse`. Backend мастерской, каталог, платежи, модерация, хранилище —
проприетарные в `synapse-cortex`. Контент авторов принадлежит авторам.

**Причина.** Godot MIT; MIT ничего не ломает юридически, позволяет автору экспортировать и
продавать игру где угодно и является причиной выбрать этот конструктор. Экспорт в standalone
нельзя запретить лицензией технически.

**Отклонено.** Source-available с запретом коммерции вне платформы (неисполнимо); BSL
(любой продающий автор формально нарушает); открытое ядро + коммерческая редакция (лишнее
трение для инди).

**Пересмотр.** Перед фазой 7 и при любом изменении лицензионной модели.

## D-002 · Комиссия только с транзакций через инфраструктуру платформы — 2026-11-02

**Решение.** 10–15% с суммы после вычета платёжной комиссии, только когда деньги реально
проходят через платформу. Продажи в Steam, itch.io, на своём сайте, донаты по внешним ссылкам,
оплата community-серверов напрямую владельцу — без комиссии.

**Причина.** Облагать то, что не проходит через серверы платформы, юридически слабо и
технически неисполнимо; это отпугнуло бы авторов.

**Пересмотр.** Фаза 7, после юридического аудита.

## D-003 · Пользовательский код на платформе не исполняется по умолчанию — 2026-11-02

**Решение.** Публичная платформа принимает декларативный контент и проверенные модули.
Произвольный код запускается локально или в отдельно экспортированном приложении.

**Причина.** Хеш, подпись, манифест разрешений и отдельный процесс не являются песочницей.
Изоляция требует отдельной модели угроз и бюджета.

**Пересмотр.** Фаза 8, только после проекта изоляции и нагрузочных тестов.

## D-004 · Два репозитория, граница «всё для локальной сборки — в MIT-репозитории» — 2026-11-02

**Решение.** Всё, что нужно автору, чтобы собрать, запустить и продать игру без платформы,
обязано находиться в `synapse`. `synapse-cortex` не может содержать обязательный для сборки код.

**Причина.** Иначе MIT-обещание нарушается тихо, а авторы теряют возможность экспорта.

**Проверка.** Каждая миссия, добавляющая функциональность, указывает, в каком репозитории она
живёт и почему. Признак нарушения — «для сборки нужен cortex».

**Пересмотр.** Постоянно, при приёмке каждой миссии.

## D-005 · Транспорт ScriptCat переносится без переписывания — 2026-11-02

**Решение.** `tools/script-cat/` перенесён как есть (на переносе — Relay 1.7.0; позже обновлён проектом — D-023); проект настраивается
профилем (четыре источника Notion, регламент, репозиторий, ветка, папка Drive). Защищённая
зона оракула — `tools/script-cat/tests/`, `regression-tests/`, `fixtures/`, `build.mjs`,
`version-oracle.mjs`, `portability-guard.mjs`.

**Причина.** Переписывание транспорта под проект воспроизводит ровно ту проблему, из-за которой
комплект делали переносимым. Любая правка кода означает новую установку и новое хранилище.

**Пересмотр.** Если найдена ошибка транспорта — отдельная миссия в cortex с зелёными пробами.

## D-006 · Бюджет: $0 до фазы 4, затем жёсткие лимиты — 2026-11-02

**Решение.** Фазы 0–3 — без платной инфраструктуры. Альфа — не более $25/мес, бета — не более
$50/мес; превышение требует решения Мастера. Relay, официальные игровые серверы и исполнение
пользовательского кода не включаются без отдельного бюджета.

**Причина.** Ранние фазы проверяют спрос, а не способность платить за железо.

**Пересмотр.** Конец каждой фазы по фактическим расходам.

## D-007 · Первая миссия — локальный каркас ядра, а не платформа — 2026-11-02

**Решение.** Следующая миссия (SYN-1) — фаза 1 в `synapse`: GameSpec, манифест модуля,
разрешение зависимостей, валидатор, разделение определение/состояние/представление, CLI,
локальный runtime, лицензионные файлы.

**Причина.** Ни один архитектурный принцип нельзя проверить без каркаса; платформа без ядра
не проверяет ничего.

**Пересмотр.** После приёмки SYN-1.

## D-008 · Пять ролей: Coordinator, Executor Core, Executor Cortex, Auditor, Warden — 2026-11-02

**Решение.** Роли заведены в Notion со статусом `Ждёт` (Agent URL заполняет Мастер):
_Имена изменены перед запуском фазы 1 — см. D-021._

`Coordinator` (Coordinator), `Executor Core` (Executor, репозиторий `synapse`),
`Executor Cortex` (Executor, репозиторий `synapse-cortex`), `Auditor` (Auditor), `Warden` (Reviewer).
Опции поля `Кому` — `Executor Core`, `Executor Cortex`, `Auditor`.

**Причина.** Ограничение Arena «один агент — один репозиторий» требует двух исполнителей, иначе
фаза 1 в `synapse` недостижима. Reviewer (Warden) рабочих карточек не получает.

**Следствие.** Пока роли в статусе `Ждёт`, миссии не активируются: цикл не должен стартовать
на недонастроенных ролях.

**Пересмотр.** При изменении состава агентов; имена ролей и `Кому` меняются синхронно.

## D-009 · Целевой автор: ИИ-агент первичен, человек вторым — 2026-11-02

**Решение.** Основной сценарий — ИИ-агент собирает игру из данных и композиции модулей.
Человеческий путь важен, но вторичен: подсказки и редактор не должны блокировать ИИ-путь.
Ручной правки ядра под конкретную игру быть не должно.

**Следствие.** GameSpec и сообщения валидатора проектируются как машиночитаемые и
человекопонятные одновременно; CLI без интерактивных вопросов.

**Пересмотр.** Фаза 2 по результатам тестов с авторами.

## D-010 · Первая категория игр: 2D top-down выживание с крафтом — 2026-11-02

**Решение.** Первый сквозной пример (фазы 1–2) — небольшая 2D игра сверху с циклом
«собирай — крафти — выживай»: одна карта, 3 типа противников, ограниченный набор предметов.
Минимальный мир — тайловая карта; воксельность в первой игре не используется.

**Причина.** Покрывает сразу несколько независимых осей (движение, спавн, бой, инвентарь,
крафт, представление) при малом объёме контента; легко проверяется скриншотами и
детерминированными прогонами. Блочный стиль останется визуальной темой, а не включением
строительства — это проверка принципа «тема ≠ механика».

**Отклонено.** Платформер (слабо проверяет модель мира), пошаговая тактика (сильно другой
цикл — лучше как второй прототип в фазе 3).

**Пересмотр.** Фаза 3: второй прототип с заметно другими правилами.

## D-011 · CLI ядра — Godot-скрипт, без второго рантайма — 2026-11-02

**Решение.** Команды `validate`, `resolve`, `run` выполняются Godot-скриптом
(`godot --headless --path … --script res://cli/synapse.gd -- …`). Отдельный Python/Node-рантайм
в ядро не вводится.

**Причина.** Один рантайм — меньше зависимостей, `NOTICE` проще, авторам не нужно ставить
второй язык. Godot уже обязателен.

**Следствие.** Скорость CLI ограничена стартом Godot (доли секунды — приемлемо).
Если появится необходимость в отдельном процессе — это ADR, а не тихая замена.

**Пересмотр.** Фаза 2, если CLI станет узким местом.

## D-012 · Drive Gateway переиспользуется, второй проект регистрируется в нём — 2026-11-02

**Решение.** Отдельный Apps Script не разворачивается. В существующем Gateway регистрируется
проект `synapse` (`CF_SETUP_PROJECT_ID` = UUID профиля ScriptCat,
`CF_SETUP_PROJECT_FOLDER` = `synapse`), выпускается отдельный проектный ключ. Старый проект
и его ключи не затрагиваются.

**Причина.** Меньше точек отказа и меньше поводов хранить вторую копию широких Drive-разрешений.
Реестр проектов в шлюзе уже поддерживает изоляцию по проекту.

**Следствие.** Папку `Arena/synapse` нельзя создавать заранее — шлюз не присоединяет
существующие папки. Порядок — `docs/setup/notion-ids.md` §3.

**Пересмотр.** Если понадобится отдельный Google-аккаунт для платформы.

## D-013 · Английский — единственный источник истины для строк — 2026-11-02

**Решение.** Все пользовательские строки пишутся сначала на английском в каталог `en`. Остальные
семь языков — переводы. Смысловая правка идёт в `en`, затем переливается в остальные.

**Причина.** Иначе получается восемь расходящихся источников, и любая новая функция умножает
работу на восемь. Английский также совпадает с языком кода, ключей и документации.

**Следствие.** Ключ стабилен и не зависит от текста; правка формулировки не меняет код.
Строка-литерал в UI или в сообщении валидатора считается дефектом.

**Пересмотр.** Не пересматривается. Может измениться только состав локалей.

## D-014 · Четыре слоя локализации с разными владельцами — 2026-11-02

**Решение.** L1 runtime игры, L2 контент игры, L3 инструменты автора, L4 платформа. L1–L3 живут
в `synapse` и работают без платформы; L4 — в `synapse-cortex`. Набор из восьми локалей
фиксирован: `en` (по умолчанию), `ru`, `zh-Hans`, `ja`, `pt-BR`, `de`, `fr`, `ko`.

**Причина.** Godot даёт только подсистему перевода строк. Если считать, что «движок уже
мультиязычный», то забываются метаданные каталога, ошибки CLI, поиск, письма и юридические
тексты — а именно они ломаются первыми.

**Следствие.** Внутри платформы и API — BCP-47, на границе с Godot — таблица соответствия
(`zh-Hans ↔ zh_CN`, `pt-BR ↔ pt_BR`). Смена языка не может менять правила игры: это тот же
принцип, что «тема ≠ механика».

**Пересмотр.** При добавлении локали — правка одной таблицы и одного списка.

## D-015 · Диагностика отделена от текста: код + параметры, перевод — представление — 2026-11-02

**Решение.** Валидатор и CLI отдают структурированную ошибку
(`code`, `path`, `expected`, `actual`) и отдельно её локализованный текст. Код и параметры
никогда не переводятся и не меняются от локали.

**Причина.** Оракул миссий, тесты и ИИ-агенты читают вывод команд. Если проверка зависит от
языка, смена локали ломает приёмку — а localization-тест начинает «проходить» только на `en`.

**Следствие.** Требование к оракулу: любая проверка ошибок опирается на `code`, а не на текст.
Оракул дополнительно проверяет, что сообщение на не-английской локали сохраняет имя поля и
фактическое значение.

**Пересмотр.** Не пересматривается.

## D-016 · Шрифты: OFL-семейства с CJK-сабсетами, бюджет 25 МБ на игру — 2026-11-02

**Решение.** Латиница и кириллица — Noto Sans; CJK — сабсеты Noto Sans JP/SC/KR, собранные
`pyftsubset`. Все шрифты в `NOTICE` (OFL). Текст в текстуры не впечатывается.

**Причина.** Godot не содержит CJK-глифов: без fallback китайский, японский и корейский
рисуются «тофу»-квадратами. Полные CJK-файлы весят десятки мегабайт каждый и раздувают
standalone-экспорт, который обязан оставаться удобным для автора.

**Следствие.** Обязательный рендер-тест на `ja`, `zh_CN`, `ko` (проверка на тофу-глифы) и
замер размера сборки в фазе 2.

**Пересмотр.** Если 25 МБ окажется мало для читаемости иероглифов — расширяем сабсеты с
пересмотром лимита.

## D-017 · Юридически значим один язык, остальные — «для удобства» — 2026-11-02

**Решение.** Аутентичной версией ToS, политики возвратов и платёжных условий считается одна
языковая версия (предложение — английская). Переводы публикуются с явной оговоркой, что при
расхождении действует аутентичная версия. До фазы 7 финальный выбор подтверждает юрист.

**Причина.** Восемь равноправных юридических версий означают восемь расхождений, каждое из
которых может быть истолковано против платформы.

**Следствие.** Платёжные и юридические тексты не переводятся машинно без ревью юриста.

**Пересмотр.** Только по заключению юриста перед фазой 7.

## D-018 · Порог качества перевода зависит от типа текста — 2026-11-02

**Решение.** UI инструментов и CLI: машинный черновик, к фазе 1 — ≥ 95 % ключей на семи языках,
к публичной бете — 100 % с выборочным нативным ревью. Метаданные каталога — нативное ревью перед
фазой 5. Юридические тексты — юрист (D-017). Документация — полностью `en` и `ru`, остальные
языки по спросу. Глоссарий продукта обязателен и един для всех языков.

**Причина.** Тратить нативное ревью на все строки сразу дорого, а на витрину и юридические
тексты — обязательно: там ошибка стоит доверия и денег.

**Следствие.** В CI появляются `i18n-check`, `i18n-coverage`, `i18n-placeholders`, `i18n-pseudo`,
`i18n-no-literals`, `i18n-fonts` (см. `docs/I18N.md` §7).

**Пересмотр.** По результатам публичной беты.

## D-019 · Переводы делают только ИИ-агенты; аутентичная юридическая версия — английская — 2026-11-02

**Решение (ответ Мастера на §10 `docs/I18N.md`).**
1. Юридически значима **английская** версия ToS, политики возвратов и платёжных условий
   (уточняет D-017). Остальные семь — переводы «для удобства», с явной оговоркой о расхождении.
2. Нативных ревьюеров нет и бюджет на них не выделяется: **все восемь локалей делаются
   агентами**. Носитель не является условием готовности ни на одной фазе.
3. **Ни один язык не снимается.** Если объёма не хватает, урезается объём перевода (сначала
   документация и длинные описания), а не состав локалей.

**Процесс.** Автор строки (пишет `en`) ≠ переводчик ≠ проверяющий:
- перевод делает агент-исполнитель, у которого есть глоссарий и каталог;
- проверяет **другой** агент без истории этого перевода — читает только `en`, перевод и глоссарий;
- для юридических, платёжных и «ключевых» строк (заголовки кнопок, ограничения, ошибки
  безопасности) — **обратный перевод** `xx → en` и сравнение смысла с источником;
- глоссарий продукта версионируется вместе с каталогами: расхождение термина — дефект, а не стиль.

**Порог качества (заменяет «нативное ревью», D-018).** Дефекты класса A недопустимы и валят
проверку: изменён смысл ограничения, сломаны плейсхолдеры, нарушен глоссарий, есть тофу-глифы,
текст обрезан или вылезает. Дефекты класса B (стиль, неестественность) допустимы: они
исправляются по сигналу — отзывом пользователя, находкой Locale Auditor, жалобой поддержки.

**Причина.** Без носителей единственная защита от «понятно, но неправильно» — независимая
проверка другим агентом плюс машинные ворота. Ослаблять состав локалей нельзя: язык — это
рынок, а не украшение.

**Следствие.** В ToS появляется оговорка об аутентичной английской версии; юрист нужен один раз
на английский текст, а не восемь раз. В платформе (фаза 5+) появляется кнопка «предложить
исправление перевода» — это бесплатный источник ревью.

**Пересмотр.** Если появится бюджет на носителей или пойдут систематические жалобы на
конкретный язык.

## D-020 · Состав ролей: три зоны и активация по появлении зоны — 2026-11-02

**Решение.** Роли фазы 1: **Warden** (`Reviewer`), **Coordinator**, **Executor Core** (`synapse`),
**Executor Platform** (`synapse-cortex`), **Spec Auditor**, **Contract Architect**,
**Locale Auditor** — семь.
Роль заводится тогда, когда появляется её зона, а не «на будущее».

**Три зоны у каждого пути репозитория:**
| Зона | Что можно |
|---|---|
| Своя | править всё, что проходит гейт |
| Чужая | только читать; правка — карточкой владельцу |
| Оракул | только дополнять; ослаблять нельзя никому — включая Warden и Coordinator |

**Правила.** Одна зона — один владелец. Аудитор не пишет код проверяемого; аудитор может
**добавлять** проверки и не может ослаблять или удалять существующие. Гейт роли — команда с
порогом, а не «отчёт приложен».

**Отложенные роли (появятся вместе со своей зоной):** Pack Author — фаза 3, Studio/Editor —
фаза 2–3, Backend/Workshop — фаза 4, Security & License Auditor — фаза 4 (аккаунты, загрузки,
чужие лицензии), Realtime Runtime — фаза 6, Assets & Animation — фаза 8.

**Причина.** Роль без зоны — простой и лишний ход в цикле; зона без владельца — дефект, который
никто не чинит. Девятнадцать ролей на старте превращают очередь в список ожидающих.

**Следствие.** `Contract Architect` и `Locale Auditor` заводятся в базе «Роли» со статусом
`Ждёт` и активируются Мастером, когда появятся их Agent URL. `Spec Auditor` один и покрывает
спецификацию, детерминизм и целостность; разделение на Runtime/Security — при росте объёма
проверок, не раньше фазы 4.

**Пересмотр.** Когда объём проверок превысит один проход, или когда появится зона, требующая
отдельной квалификации (безопасность, платежи).

## D-021 · Имена ролей заморожены: Executor Platform, Spec Auditor, Contract Architect — 2026-11-02

**Решение.** Перед запуском миссии состав и имена окончательные:

`Warden` (`Reviewer`) · `Coordinator` · `Executor Core` · `Executor Platform` · `Contract Architect`
· `Spec Auditor` · `Locale Auditor`.

Переименовано относительно D-008 и D-020:
| Было | Стало | Почему |
|---|---|---|
| `Executor Cortex` | `Executor Platform` | «Cortex» и «Core» различаются одной буквой и путаются при выборе `Кому`; «cortex» — имя нашего репозитория, а не зона. «Platform» называет зону однозначно |
| `Auditor` | `Spec Auditor` | «Auditor» без предмета — вопрос «чего именно?». Зона роли — соответствие контрактам и ТЗ; при росте объёма из неё выделится `Runtime Auditor` (детерминизм, fuzz, бюджеты) |
| `Architect` | `Contract Architect` | «Architect» без предмета. Предмет у роли один: контракты (`GameSpec`, манифест, коды ошибок) и ADR |

`Warden` и `Coordinator` не переименовываются: эти имена закреплены Мастером.

**Причина.** Имя роли попадает в промпт агента, в выпадающий список `Кому` и в отчёт. Неоднозначное
имя стоит одного-двух неверных ходов на каждом цикле, а исправить его после выпуска карточек
нельзя без потери истории.

**Следствие.** Маршрутизация `roleRepos` в профиле ScriptCat привязана к **ID страницы** роли, а не
к имени, поэтому переименование маршруты не рвёт. Но опции `Кому` в «Запросах» и имена в профиле
должны совпадать с базой «Роли» — иначе транспорт откажется выдавать карточку. Пока карточек нет,
переименование бесплатно. После первой выданной карточки имена не меняются.

**Пересмотр.** Запрещён: имя роли — часть контракта команды.

## D-022 · Изоляция репозиториев: роли ядра видят только ядро — 2026-11-02

**Решение.** `Executor Core`, `Contract Architect`, `Locale Auditor` имеют доступ только к
`synapse` и не видят `synapse-cortex`. `Warden`, `Coordinator`, `Executor Platform`,
`Spec Auditor` работают в `synapse-cortex`: они видят оба репозитория, но писать в `synapse`
не могут. Маршруты ролей в ScriptCat это не обходят: коннектор — основной путь, кнопки
транспорта — аварийный.

**Следствие 1.** Авторитетные документы контрактов и локализации ядра (слои L1–L3) живут в
`synapse`: `docs/contracts/`, `docs/i18n/`, `docs/adr/`, `locales/`, `tools/i18n/`. В cortex
остаются платформенная часть (L4) и журнал проектных решений. Что именно переносится —
`docs/handoff/core-contracts-i18n.md`.

**Следствие 2.** Требование доходит до роли ядра карточкой или «Регламентом» в Notion, а не
ссылкой на файл в cortex. Ссылка на `synapse-cortex` внутри `synapse` — дефект.

**Следствие 3.** Согласованность ядра и платформы проверяет Warden: только он читает оба
репозитория. Это его нагрузка, а не побочный эффект.

**Следствие 4.** Для платформенных контрактов и локализации L4 (фазы 4–7) нужен отдельный
проверяющий на стороне cortex либо экспорт каталогов и схем в артефакт. Решение — перед фазой 4.

**Причина.** Изоляция — техническая гарантия INV-1, а не бюрократия. Агент ядра, который видит
закрытый код платформы, рано или поздно начнёт на него опираться, и «ядро собирается без
платформы» перестанет быть правдой. Одновременно это уменьшает поверхность утечки: у агента с
доступом только к MIT-репозиторию нечего уносить.

**Пересмотр.** Если роль ядра упрётся в требование, которое нельзя выразить карточкой, —
требование переписывается в контракт внутри `synapse`, а не открывается доступ.

## D-023 · Регламент приходит агенту в промпте, а не ссылкой

Дата: 2026-11-03. Статус: принято Warden в пределах полномочий (процесс, не продукт).

**Проблема.** Транспорт передавал регламент ссылкой (`roleContext` → `Регламент: <pageUrl>`),
и каждый агент каждый ход сам читал страницу Notion: ~50 блоков, несколько вызовов API, сырой
JSON в ответе. Дорого, медленно и хрупко — при обрезке ответа агент видит половину правил
и не знает об этом. Переезд на Google Drive это не лечит: там нет правки по блокам и стабильных
ID, а запись идёт через Apps Script Gateway.

**Решение.** Краткая версия регламента (`docs/regulation-digest.md`) вшивается в бандл при сборке
и попадает в каждый промпт блоком `=== CF_REGULATION ===`. Полная версия остаётся справочником
по ссылке. Оракул против расхождений — `tools/script-cat/regulation-oracle.mjs`:

- ровно один плейсхолдер `@@REGULATION_DIGEST@@` в исходниках;
- вшитый текст равен `docs/regulation-digest.md` (иначе сборка не сходится);
- версия краткой копии равна версии `docs/REGULATION.md` (иначе сборка падает);
- бюджет объёма ≤ 9000 знаков: вход хода обязан оставаться коротким;
- проба `tests/relay-regulation-digest-smoke.mjs` проверяет и сам промпт, и деградацию без текста.

**Цена и выгода.** +~2000 токенов на промпт против 5–10 вызовов чтения страницы: дешевле
и, главное, детерминированно — правила не зависят от квоты, обрезки ответа и порядка блоков.

**Компромисс по ролям (компенсирующее правило).** Правка `tools/script-cat/**` — защищённая зона,
и владелец платформенной части — `Executor Platform`. На момент записи решения роль была в статусе
«Ждёт», поэтому карточку транспорта исполнил Warden, но не принимал сам: приёмка — оракул
(`npm run verify`, включая guard переносимости и пробы сборки), и решение зафиксировано здесь.
**Действует до 2026-11-02.** `Executor Platform` активирована (Agent URL заполнен), поэтому
исключение закрыто: дальнейшие правки `tools/script-cat/**` — только её карточками или отдельной
миссией, приёмка Warden по D-020. Дописанное в этот раз остаётся как есть: оно покрыто D-023
и зелёным оракулом, переделывать задним числом нечего.

**Откат.** Убрать плейсхолдер из `src/01-config.js` и блок из `21-prompts.js`, пересобрать бандл:
агент снова получает только ссылку, остальное не меняется.

**Не решено здесь.** `AGENTS.md` в `synapse` содержит устаревшее «the repository is private»
(репозиторий публичный) и не описывает модель двух репозиториев. Правка — карточка K-13
в очереди SYN-1, исполнитель `Executor Core`: Warden в `synapse` не пишет (D-022).

## D-026 · Формат ответа — в конце задания, а не после регламента — 2026-11-03

**Что случилось.** Первый ход Координатора (2026-11-03) занял десятки вызовов инструментов.
Он заново вычитывал страницу регламента и ТЗ миссии блоками по 4–5 (ответ `get_block_children`
обрывается), затем долго искал точный формат строки `CF_COORDINATOR_RESULT` — в Notion, в Drive,
вспоминал по прошлым задачам. Карточка K-1 в итоге создана верно (`40c6f0cf-5705-8137-85c3-d4d1d4850be5`:
Кому `Executor Core`, `Dispatch State = Ready`, `Sequence = 1`, Scope и оракул покрывают проверки),
но цена хода — недопустимая.

**Причина — не «глупость» агента, а порядок в промпте.** С D-023 блок регламента (~6 000 знаков)
стоял **последним** в промпте, после блока «ПОРЯДОК» с маркером. Конец промпта модель читает
внимательнее, чем середину, и служебная строка оказывалась именно в середине. Плюс никто не сказал
Координатору, что регламент уже пришёл: он пошёл читать страницу, а каждый ответ Notion на 10–20 тысяч
знаков вытеснял из контекста остальное — включая формат ответа.

**Решение.**
1. `roleContext(role)` перенесён сразу после `technicalInfo` во всех пяти сборках промпта
   (`executorPrompt`, `coordinatorPrompt`, `reviewPrompt`, `answerPrompt`, напоминание о маркере).
   Промпт теперь **заканчивается** порядком работы и маркером.
2. В техблок Координатора добавлено прямым текстом: регламент уже вшит (`=== CF_REGULATION ===`),
   страницу открывать не нужно; формат финальной строки — в конце промпта; маркер не восстанавливают
   по памяти, из Notion, Drive и других проектов; ТЗ читается по делу, а не целиком блоками по 4.
3. В краткий регламент (1.5) добавлено то же правило в общем виде — оно действует для всех ролей.
4. Проба `relay-regulation-digest-smoke.mjs` проверяет **порядок**: в промптах исполнителя и
   Координатора `roleContext` стоит до блока с маркером. Вернуть регрессию молча нельзя.

**Следствие.** Промпт Координатора стал читаться как «правила → задание → что именно прислать
последней строкой». Если маркер всё же потерян, правильное поведение — сдать отчёт и сказать
«маркер не виден»: транспорт напомнит сам (`markerReminders`), вместо того чтобы искать формат
в чужих базах.

**Не решено здесь.** ТЗ миссии всё ещё читается через `get_block_children` — это десятки вызовов
на страницу. Отдельная карточка: вшивать краткое ТЗ (цель, оракул, инварианты) в промпт Координатора
тем же механизмом, что регламент.

**Пересмотр.** После второго-третьего хода Координатора: если поиск формата повторится, причина
в другом месте.

## D-027 · Автоцикл: Warden решает сам, транспорт меняется только в окно паузы — 2026-11-03

**Контекст.** Мастер запускает автоцикл: агенты работают и мержат в `main` непрерывно, без остановок
на подтверждение. Одновременно действует ограничение среды: `relay.user.js` устанавливается в браузер
**вручную Мастером**, автообновления нет. Значит, правка транспорта не действует до переустановки,
а её последствия видит не тот, кто её слил.

**Решение.**

1. **Полномочия.** В автоцикле все решения принимает Warden: состав и порядок карточек, трактовка
   неоднозначностей, `accept` / `rework`, изменения контрактов и оракулов в рамках уже принятых
   решений, признание карточки `Blocked`, перепланирование. Цикл останавливается **только** если
   без Мастера технически невозможно: нет доступа, нет агента, нужна переустановка userscript,
   платный ресурс, лицензия/деньги/ToS.
2. **Синхронизация.** Каждый ход Warden начинается с `git fetch origin && git reset --hard origin/main`
   (клон shallow, `merge` между снимками даёт «unrelated histories»). Работа ведётся в ветке сессии,
   мерж — в `main`, после мержа ветка снова выравнивается по `origin/main`.
3. **Транспорт — отдельный гейт.** Любая правка `tools/script-cat/**`:
   - обязана поднять `@version` **и** `SCRIPT_VERSION` (одно без другого запрещено);
   - мержится только в окно паузы, а не в момент выдачи хода;
   - в PR и в сообщении Мастеру помечается «нужен ручной апдейт ScriptCat»;
   - после мержа Warden **не** считает изменение действующим: пока userscript не переустановлен,
     работает прежняя версия, и промпты агентов — прежние.
   Пока автоцикл идёт, Warden транспорт не трогает: изменения копятся в очередь и садятся одним
   батчем в ближайшее окно паузы.
4. **Причина правила — уже случившийся дефект.** PR #26 и #27 изменили поведение транспорта
   (`src/08-projects-ui.js`, `relay.user.js`, +78 строк) **без** подъёма `@version`: в `main` лежит
   транспорт, который по номеру неотличим от предыдущего. `version-oracle.mjs` такое не ловит — он
   сверяет шапку со `SCRIPT_VERSION`, а не «контент изменился → номер обязан измениться».

**Следствие.** Вводится машинная проверка (карточка транспорта, окно паузы): сборка пишет в бандл
отпечаток исходников, а проба сравнивает отпечаток и `@version` с предыдущим состоянием `main`;
изменение контента без смены версии — красная проба. До её появления действует правило 3 и ручная
проверка Warden перед мержем.

**Побочный дефект, найденный сразу.** Версия полного регламента, версия краткой копии и номер
транспорта жёстко связаны: `regulation-oracle.mjs` требует `версия digest == версия REGULATION`,
а сборка вшивает digest в бандл. Значит **любая** правка `docs/REGULATION.md` (даже абзац про
транспорт) вынуждает выпуск userscript и ручную переустановку у Мастера. Поэтому правила автоцикла
пока живут в `DECISIONS.md`, `WARDEN.md`, очереди карточек и Notion (поле «Гейт» роли), а не в
`REGULATION.md`; развязка версий — первый пункт карточки K-14 (digest объявляет, какую версию
полного регламента он отражает, и имеет свой счётчик).

**Уточнение по факту (2026-11-03, после выпуска D-027).** Мастер подтвердил: правки #26/#27 он сам
заказал агенту ScriptCat, экспорт и импорт конфигурации у него в браузере работают. Аварии нет.
Поэтому отдельный релиз «только ради номера» **не выпускается**: `@version` поднимается при ближайшем
плановом релизе транспорта (батч вместе с K-14), а не сейчас — иначе Мастер делает лишнюю ручную
переустановку ради косметики. Остаётся один изъян, и его надо помнить: под номером 1.8.2 существуют
**две разные сборки** (до #26/#27 и после), значит номер перестал быть признаком актуальности. До
появления отпечатка (K-14) в переписке версия всегда сопровождается SHA: «1.8.2 @ 9f8c447», а
проверка «что стоит в браузере» делается по поведению (экспорт/импорт), а не по цифре.
Запись в поле «Гейт» роли Executor Platform и правило 3 не меняются: они про будущие правки.

**Ограничение, которое надо назвать честно.** Пауза — это кнопка в браузере Мастера; агент её нажать
не может. Поэтому «тормози автоцикл» для Warden означает: не мержить транспорт в активном цикле,
заранее собрать батч и явно попросить паузу с точной версией для переустановки. Молчаливая правка
транспорта в автоцикле запрещена.

**Пересмотр.** Когда появится автообновление userscript из `main` (или его сможет ставить агент) —
гейт 3 снимается, правило 4 остаётся.

## D-028 · Состояние карточки — производное от факта, а не наоборот — 2026-11-03

**Контекст.** K-15 выполнена и слита в `main` (`synapse` PR #5, merge `e19a8d3`, 11:40:26Z), отчёт
сложен в Drive в 11:41 — а строка «Запросы» осталась `Running` / `Check=fail` / без `PR` и без
`Submitted At`, и в 12:46 транспорт выдал ту же карточку повторно с заданием «пояснить маркер
check=1». Разбор — `docs/incidents/2026-11-03-k15-reconciliation.md`. Похожая схема была на K-3:
три возврата подряд при частично зелёных проверках.

**Решение.**

1. **Источник истины.** Факт работы — merge в GitHub и отчёт в Drive с маркером. Поля карточки
   (`Dispatch State`, `Check`, `PR`, `Submitted At`, `Run ID`) — производные. При расхождении верен
   факт; карточку приводят к факту, а не наоборот.
2. **Warden не судит по `Check`.** Перед любым решением по карточке Warden проверяет GitHub (PR,
   merge SHA) и отчёт в Drive. `Check=fail` без отрицательного доказательства и без смерженного PR —
   сигнал о сбое транспорта, а не о провале работы. В отчётах и «Итоге» пишется факт со ссылкой на
   merge SHA; `Check` цитируется только как состояние карточки.
3. **Терминальная запись до следующей выдачи.** Транспорт пишет `Submitted` + `Check` + `PR` +
   `Submitted At` + `Run ID` одним обновлением и не выдаёт карточку повторно, пока запись не
   подтверждена.
4. **Неизвестное ≠ fail.** Неразобранный или отсутствующий маркер даёт `Check=none` и
   `Blocked` с причиной; `fail` — только по явному отрицательному результату.
5. **Замок по факту и лимит повторов.** Карточка со смерженным PR или `Check=pass` не выдаётся
   повторно; повторная работа — только явным `Rework`. Не более двух автоматических повторов, третий
   — `Blocked` с записью «требуется решение Warden».
6. **Журнал причин выдачи.** Каждая выдача оставляет строку: тип (первичная / повтор / `Rework`),
   сработавшее условие, значение маркера.
7. **Сверка при старте.** После паузы, перезапуска браузера или потери сессии транспорт сверяет
   последнюю выдачу с логом в Drive по `dispatch_id` и приводит состояние к найденному факту.
8. **Своя ошибка называется своей.** Сбой разбора маркера нельзя объяснять недоступностью токена или
   сети; в сообщении — сырой маркер, строка и ошибка разбора.

**Практика немедленная.** До выпуска правил 3–7 в транспорте Warden в каждом ходе сверяет карточки
по GitHub и Drive вручную и явно пишет в отчёте, какие состояния в Notion устарели. Повторные выдачи,
вызванные `Check=fail`, не переиздаются и не пересдаются: работа принимается по факту мержа.

**Отклонено.** «Доверять `Check`, потому что его пишет транспорт» (именно это и породило ложный
провал); «перевыдавать карточку, пока не станет `pass`» (бесконечный цикл, трата квоты и времени);
«чинить руками каждый раз» (не масштабируется и скрывает дефект).

**Пересмотр.** После выпуска правил 3–7 батчем вместе с K-14; тогда пункт «практика немедленная»
снимается.

**Уточнение: причина найдена (журнал транспорта, 11:31–15:51).** Дело не в разборе маркера. Транспорт
искал PR **не в том репозитории** и принимал совпадение номера за подтверждение: по карточке K-2
записан `synapse-cortex/pull/2` («Шлюз: детальная инструкция», merge 2026-11-02T13:35:11Z), по K-3 —
`synapse-cortex/pull/3` («Supabase: состояние проекта», merge 2026-11-02T14:05:19Z), тогда как
настоящие PR — `synapse` #2 (09:06:09Z) и #3 (10:16:44Z). Ложный merge рассыпался на проверке
ответа, и транспорт обнулял `Submitted At`/`PR`/`Run ID`, из-за чего карточка снова выглядела
невыданной — отсюда K-2 ×3, K-3 ×3, K-15 ×4. Когда репозиторий определялся верно, включалась
обратная ошибка: «PR относится к `synapse`, а цель выдачи работает с `synapse-cortex`» → пауза, то
есть правильный PR отвергается как чужой. И отдельно: токен не видит `synapse` вовсе.

**Дополнение к решению.**

9. **Целевой репозиторий — свойство карточки.** Все проверки (поиск PR, запись merge, проверка
   ответа) идут только по нему; репозиторий, в котором работает транспорт, не подставляется.
10. **Идентичность PR, а не номер.** Подтверждение — по URL, `headRefName` и `baseRefName` из
    GitHub. «Не вижу PR», «PR не смержен» и «смержен другой PR» — три разных ответа.
11. **Три состояния.** `pass` / `fail` / `unconfirmed`. Неподтверждённое — `Check=none` +
    `Blocked`, терминальные поля не очищаются, повторной выдачи нет.

Полный список исправлений — `docs/incidents/2026-11-03-k15-reconciliation.md`, раздел «Что должен
сделать транспорт». Он входит в батч K-14; правки транспорта по-прежнему только в окно паузы.

## D-029 · Внешний пилот: одноразовые агенты, бриф как оракул — 2026-11-03

**Контекст.** Целевой автор — ИИ (D-009). Оракулы миссий проверяют код, но не проверяют главное
обещание продукта: «ИИ-автор может сделать игру, читая только публичную документацию». Мастер
предложил периодические миссии, в которых свежие агенты проходят путь автора целиком.

**Решение.**

1. **Пилот — миссия, не роль.** `SYN-P1 · Внешний пилот` с собственным оракулом; черновик ТЗ —
   `docs/missions/SYN-P1.md`.
2. **Каждый прогон — новый агент.** Без роли в «Ролях», без доступа к `synapse-cortex`, без Notion,
   без истории прошлых прогонов. Постоянной роли «тестировщик» не заводим: агент, живущий в цикле,
   обрастает контекстом и проходит тест по памяти (риск R-05 в новой форме). Владелец процесса
   пилотов — не раньше фазы 2, когда прогоны станут регулярными (D-020: роль заводится вместе с зоной).
3. **Бриф — оракул.** Версионируется, замораживается вместе со стартовым SHA; менять — только
   осознанно с записью причины. Подгонять бриф под результат нельзя.
4. **Выход прогона — карточки, а не отчёт.** Каждое «застрял здесь» становится задачей на
   документацию, UX, сообщение валидатора или ошибку. Отчёт без карточек считается несданным.
5. **Метрики сравнимы.** Время до первой запущенной игры, число вопросов, число обращений к
   исходникам, число явных «допущений» — по одному протоколу и шаблону.
6. **Пилот не производит контент.** Критерий успеха — понятность и воспроизводимость пути, а не
   выпущенная игра. Релиз игры в оракул не входит, пока нет каталога и фазы публикации.

**Отклонено.** Постоянная роль тестировщика (перестаёт быть внешней); «дать агенту доступ к нашим
докам и чатам» (тест перестаёт быть тестом); гонять каждый день (квота без прироста информации).

**Пересмотр.** После трёх прогонов — ревизия брифа и метрик; при регулярности — вопрос о владельце
процесса в фазе 2.

**Контекст.** По K-11 требовалось подтвердить, кому принадлежат права на ядро `synapse` и кто

**Ответ Мастера (2026-11-03).** Правообладатель — **Creative36711** (псевдоним), год — **2026**,

вносятся и для лицензирования не требуются.

**Решение.**

1. Строка copyright в `LICENSE` остаётся в виде `Copyright (c) 2026 Creative36711`. Правка не

   указан в истории репозитория.
4. `NOTICE` и раздел README остаются как есть: MIT распространяется на оригинальное ядро;

5. Если ядро перейдёт к юрлицу — в `LICENSE` добавляется новая строка copyright, старая сохраняется.

6. O-9 в «Итоге» SYN-1 закрывается: файлы на месте (проверено на `synapse` `0b680a3`, PR #7 —

**Оговорка.** Warden не юрист и не даёт правовых гарантий: решение фиксирует волю правообладателя,
а не заменяет юридическую консультацию по конкретной юрисдикции. Если появится коммерческое
использование или спор — вопрос к юристу, файл к этому готов.

**Пересмотр.** При смене правообладателя (юрлицо, соавторы, продажа), при переходе на другую
лицензию, при добавлении компонентов с несовместимыми лицензиями.

## D-031 · Артефакты живут в Arena/synapse/artifacts, а не в корне Drive — 2026-11-04

**Контекст.** Мастер заметил: агенты складывают отчёты в корень My Drive. На 2026-11-04 там лежало
семь файлов от пяти карточек (K-15 ×3, K-6, K-16, K-11 ×2) рядом с папками `Arena` и `Моё`. Корень
перестал быть навигацией: по нему нельзя понять, что относится к миссии, а что личное.

**Решение.** Структура и правила — `docs/drive-layout.md`. Коротко:

1. Все артефакты — в `Arena/synapse/artifacts` (ID `1fXMP8Fj35kQRSyYTbr-ji-rRnPLClPD3`). Журналы —
   в `logs/`, тексты заданий — в `payloads/`, и туда пишет только транспорт.
2. В корне My Drive не создаётся ничего, кроме папок `Arena` и `Моё`.
3. Имена: `<МИССИЯ>__<КАРТОЧКА>__<вид>__<дата или SHA>.<ext>`, только латиница, цифры, `-`, `_`, `.`.
4. Один прогон — один основной отчёт; дополнение — `__supplement-N`, а не третий «final».
5. Перемещение файлов безопасно: `id` не меняется, ссылки и поля карточек остаются верными.

6. Задним числом не переименовываем: риск порвать цитаты выше пользы. Правило — для новых артефактов.
7. Транспорт (батч K-14): проверять доступность `artifacts` на старте, указывать её ID в промпте
   исполнителя, не закрывать прогон без `Output Drive File ID`, при недоступности — писать «артефакт
   не сохранён», а не падать в корень.

**Почему не «просто попросить агентов аккуратнее».** Просьба не проверяется. Проверяется наличие
файла в конкретной папке — это и становится условием приёмки.

**Отклонено.** Подкаталог на каждую карточку (семь файлов — преждевременная иерархия); подкаталог на
каждую миссию сейчас (введём при старте SYN-P1, там артефактов будет много); массовое переименование
старого.

**Пересмотр.** При старте SYN-P1 (подкаталог `artifacts/SYN-P1/`), при превышении ~50 файлов в
`artifacts/`, при появлении бинарных артефактов большого размера.

## D-032 · Provisioning Arena-агентов — отдельный административный контур ScriptCat 1.10.0 — 2026-11-04

**Контекст.** Строки Notion «Роли» нужно обслуживать без ручной рутины: пустой
`Agent URL` → создать сессию Arena, выбрать repo, отправить bootstrap-пробник,
захватить URL, переименовать чат в имя роли, записать URL и активировать;
заполненный URL + запрос → заменить агента, сохранив старый в `Previous Agent URL`
и архивировав его. Рабочий цикл (`K.pending/K.expect`, карточки, миссии) не должен
смешиваться с административным созданием агентов.

**Решение.**

1. ScriptCat 1.10.0 добавляет provisioning-контур (`31-provision-core`,
   `32-provision-dom`, `33-provision-flow`, `34-provision-ui`). Gateway в рамках
   provisioning не менялся (**1.7.1**); впоследствии D-033 поднял Gateway до
   **1.8.0** в том же PR по команде Мастера. Публичный `synapse` не меняется.
   Контур выключен по умолчанию
   (`agentProvisionEnabled=false`, mode=manual, пустой allowlist).
2. Право одобрения — только свежая строка «Роли» с `Agent Admin=true` и
   `Статус=Активна` (предпочтительно Coordinator, иначе Reviewer). Имена ролей не
   дают права и не зашиваются в код. Админ-роли нельзя автоматически создавать,
   заменять или архивировать.
3. Создание начинается только после маркера `CF_AGENT_PROVISION_RESULT` с выданным
   `request_id`; jobs проверяются по отправленным кандидатам и свежей строке
   Notion. Команды archive/delete/activate/admin в маркере запрещены; архив старого
   агента — внутреннее следствие replace после успеха.
4. DOM-контракт Arena: repo picker через `cmdk`/`data-radix-popper-content-wrapper`,
   sidebar через `a[data-sidebar="menu-button"][href="/agent/<uuid>"]`, меню через
   `button[data-sidebar="menu-action"]`, Rename/Archive через видимые menuitem.
   Без `radix-*` id и `nth-child`. Неоднозначность → пауза. `Add repositories` не
   нажимается; уже выбранный repo не кликается повторно.
5. URL новой сессии сохраняется сразу после появления, до rename и Notion. При
   провале rename/Notion/активации новая сессия не создаётся повторно; job
   восстанавливается из GM. Автоцикл на время provisioning выключен и
   восстанавливается только после успеха без паузы.
6. Bootstrap-пробник хранится в профиле (`agentBootstrapPrompt`). В коде дефолт
   **пуст**: точный текст с проектным `owner/repo` не зашивается (противоречие ТЗ
   «default text» vs «no hardcoded project names» решено в пользу переносимости).
   Рекомендованный шаблон: «Что изображено на картинке test.jpg в репозитории
   https://github.com/OWNER/test?» — OWNER подставляет Мастер. Пробник не содержит
   CF_/Notion/cortex/REGULATION/WARDEN/DECISIONS, токенов и внутренних ссылок;
   модель не выбирается, смысл ответа не проверяется.
7. Notion-поля аддитивны (Agent Admin/State/Job ID/Created At/Previous Agent URL).
   ScriptCat не создаёт страницы и не пишет Роль/Функцию/Зона записи/Гейт/
   Репозиторий/Agent Admin. Живые записи — только в окне D-027 после отдельного
   подтверждения Мастера.

**Отклонено.** Автоматическое создание админ-ролей; одобрение по имени роли;
повторная сессия при уже захваченном URL; архив нового агента; откат успешной
замены из-за неподтверждённого архива старого; hardcoded проектные имена в коде.

**Пересмотр.** После живой приёмки D-027 (create/replace/негативные проверки),
при изменении DOM Arena или схемы Notion, при появлении continuation для
bootstrap tool-call limit.

Дата: 2026-11-04. Статус: принято Мастером командой «делай всё за один ход, что

карточка с длинным заголовком/зоной/веткой пробивает запас ~90 символов. Координатор

   `auditor.card` ≤2200 (регрессия в `prompts-smoke`). Версии изменённых блоков подняты.

   доставляет короткий verbatim-указатель. Стратегия `full → payload-указатель →
   compact → pause`. **Оракул и Scope остаются inline**; файл их не заменяет и не
   ослабляет. Малое задание остаётся инлайном. Отказ шлюза — явная ошибка/пауза.
4. **Total-лимиты в боевом пути.** `DISPATCH_TOTAL` (Executor 6500 / Auditor 5500 /
   Reviewer 7000) соблюдается доставкой, а не только оракулами.
5. Контракт `agent-protocol.json` → protocolVersion **1.3** (аддитивно); ScriptCat

   (`savePayload` уже был). Docs `protocol.md`/`drive.md`/`drive-layout.md` согласованы.

**Отклонено.** Молчаливое поднятие бюджетов; резка оракула/Scope/ID ради размера;
перекладывание оракула в payload-файл, который агент может не прочитать; тихий
инлайн при отказе шлюза; повтор неудачной выдачи без изменения причины.

**Пересмотр.** При росте фиксированного скелета (новые блоки/правила), при
появлении заданий, которые не выражаются указателем, или если агент не читает
payload-файл — тогда пересмотреть порог/канал, но не ослаблять оракул.

## D-035 · Маркер Координатора с первого раза + артефакты не в корне Диска — 2026-11-04

Дата: 2026-11-04. Статус: принято Мастером командой «исправь эти проблемы, в конце
PR и мерж» (промпты, процесс). Инциденты боевой миссии SYN-1: (1) Координатор дважды

напоминания; (2) Spec Auditor положил отчёты K-17/K-19 в корень Google Drive, а не в
`Arena/<project>/artifacts`.

**Контекст.** Разбор показал две причины. (1) Маркер стоит только в самом конце
длинного `coordinator.plan`; после десятка tool-вызовов Координатор его «не видит»,
а правило «не восстанавливай маркер по памяти» (из регламента) честно запрещает
угадывать формат — поэтому ход встаёт до напоминания. Короткое напоминание
(`reminder.marker`) работает, потому что оно свежее и маркер в нём сразу виден.
(2) Раскладку Drive (`drive.layout`) получает только Координатор; исполнитель и
аудитор в промпте не видели адреса папки `artifacts` и клали отчёты куда придётся
(то в `artifacts`, то в корень — непоследовательно). Gateway `saveArtifact` кладёт
файл правильно, но аудитор пишет своим Drive-коннектором, минуя шлюз.

**Решение.**

1. **Прайм маркера.** `coordinator.plan`/`coordinator.recovery` открывает короткий
   блок `coordinator.prime`: «заверши ход маркером последней строки; формат и IDs —
   в конце промпта, скопируй оттуда, не по памяти». Авторитетный маркер с IDs
   остаётся последним блоком. Блок прайма не несёт литерал маркера и не называется
   `marker.*`, поэтому инвариант компилятора «ровно один маркер, и он последний»
   не нарушается. Это прайминг (первичность + недавность), а не дубль формата.
2. **Адрес артефактов в промпте.** `executor.card`/`auditor.card`/`reviewer.card`
   несут короткий блок `drive.artifacts`: «Артефакты в `Arena/<project>/artifacts`,
   не корень Диска; ссылки в поле `artifacts`». Имя проекта подставляется из профиля
   (`driveFolder`), не зашито. Блок не verbatim (честный overhead) и влезает в бюджет
   `auditor.card` ≤2200 **без подъёма бюджета** (K-17-подобная карточка проходит,
   скелет ≤2050). `drive.layout` остаётся только Координатору.
3. **Уборка в Drive.** Отчёты Spec Auditor «SYN-1 K-17 O-4…» и «SYN-1 K-19 O-5…»,
   лежавшие в корне Диска, перенесены в `artifacts` (`1fXMP8Fj…`). Перенос безопасен:
   ID/URL файла не меняются, ссылки в журналах/карточках остаются валидными;
   ретро-переименование запрещено D-031, имена сохранены.
4. Контракт `agent-protocol.json` → protocolVersion **1.4** (аддитивно, секция `d035`);
   ScriptCat **1.12.0**; digest/REGULATION 1.5 и Gateway 1.8.0 не меняются. Docs
   `protocol.md`/`drive.md` согласованы; оракулы `prompts-smoke` (§12–13) и
   `docs-smoke` (protocolVersion 1.4) обновлены синхронно.

**Отклонено.** Молчаливое поднятие бюджетов ради новых блоков; дубль полного формата
маркера в начале (сломал бы «ровно один маркер»); возврат полного регламента в промпт
(он ~5000 зн. и пробил бы все бюджеты — правила уже в блоках); кеширование ID папки
артефактов из шлюза ради точного адреса (усложнение; путь из профиля достаточен и
честен); переименование перенесённых отчётов под D-031 (запрещено ретро-переименование).

**Пересмотр.** Если Координатор снова начнёт пропускать маркер после прайма —
усилить напоминание или верификацию хвоста при доставке, но не дублировать формат.
Если аудитор снова положит отчёт в корень, имея адрес в промпте, — рассмотреть
передачу точного folder ID из шлюза или принудительную проверку размещения
(`verifyArtifactPlacement`) для файлов, созданных Drive-коннектором.

## D-037 · Мультирепо-сторож ADR: предложение второго репозитория доходит до приёмки — 2026-11-05

Дата: 2026-11-05. Статус: принято Мастером («Делай все за один ход, что решил, и сразу
PR и мерж»). Инцидент: боевой вопрос по ADR `SYN-1` (репозиторий `synapse`, файл
`docs/decisions/SYN-1.md`, blob `9df95ca6…`, статус proposed) завис в «Ждёт».
Координатор задал вопрос со ссылкой на файл; предохранитель «приёмка читает файл, а не
пересказ» законно отказал дважды («Предложение не передано приёмке: полный текст не
совпадает с Git blob SHA», затем «Предложение из репозитория ещё не содержит полный
текст с SHA»), и ход ушёл дальше по очереди (K-20 → Spec Auditor). Автоцикл остановлен.

**Контекст / кто виноват.** Виноват транспорт, а не агенты и не бюджет. Полный текст с
Git blob SHA дописывает в вопрос только сторож `refreshDecisions` (раз в 10 мин). Он был
зашит на главный репозиторий профиля `C.repo`/`C.branch` (ограничение 1.8.2,
`docs/scriptcat-multirepo-synapse.md` §7). Главный репозиторий профиля — `synapse-cortex`,
и папки `docs/decisions` в нём нет: `gh api …/synapse-cortex/contents/docs/decisions` даёт
404. Запрос уходил в catch и возвращал пустой снимок — молчаливый no-op. Предложение
лежало во ВТОРОМ репозитории `synapse`, куда сторож не смотрел. Гипотеза «самолечится за
≤10 мин» опровергнута: ждать было бесполезно, вопрос висел бы бессрочно.

**Решение (бюджеты промптов НЕ подняты).**

1. **Обход всех репозиториев.** `refreshDecisions` итерирует `C.repos` (список
   `{repo, branch, main}` активного профиля); без списка — fallback на single-repo
   `C.repo`/`C.branch || "main"` (обратная совместимость).
2. **404 не роняет обход.** Отсутствие папки `docs/decisions` в одном репозитории
   (`Number(e.status) === 404`) пропускается (`continue`), остальные репозитории
   опрашиваются. Прочая ошибка по-прежнему уходит во внешний catch и возвращает прежний
   снимок `cache.rows` (без дубликатов вслепую).
3. **Составной кэш.** `cfn-adr-text` ключуется `${repo}/${file}`; плоские ключи до D-037
   мигрируются под `${C.repo}/` и не смешиваются с другими репозиториями.
4. **Строка несёт repo/branch.** `rows.push({…, repo, branch})`; `proposalQuestion` строит
   ссылку `github.com/<repo>/blob/<branch>/docs/decisions/<file>` и ключ дедупликации
   `adr-full:`/`adr-full-confirm:` из репозитория самого предложения. Строки без `repo`
   (наследие и запиненные тесты) дают прежний формат ключа — пины целы.
5. **Точнее сообщение отказа.** Когда полного текста ещё нет вообще (нет маркера
   `CF_ADR_CONTENT`), лог пишет «сторож ещё не дописал полный текст файла с Git blob SHA»,
   а не вводящее в заблуждение «не совпадает с SHA».
6. Контракт → protocolVersion **1.6** (секция `d037`); ScriptCat **1.12.2**; Gateway 1.8.0
   и digest/REGULATION 1.5 не менялись. Docs `protocol.md`/`scriptcat-update.md`/
   acceptance-report/`scriptcat-multirepo-synapse.md` §7 согласованы.

**Регрессия.** `relay-adr-multirepo-integration`: главный репозиторий без папки decisions
(404) не роняет обход; предложение второго репозитория найдено, несёт `repo`/`branch`,
доходит до доставки; ссылка и ключ из репозитория предложения; миграция плоского кэша;
одноимённые файлы двух репозиториев не смешиваются; обратная совместимость single-repo.
Существующие ADR-пины (handoff/default/feedback/stale-plan/decisions) не ослаблялись.

**Ограничение.** Дедупликация `adrRefsOf`/`sameQuestionRow`/`decidedAdrNames` идёт по
имени файла (`file:<имя>`) кросс-репо: имена ADR должны быть уникальны в профиле.
Одноимённые файлы в разных репозиториях считаются одним предложением по имени.

**Отклонено.** Вариант B — догружать файл прямо в `startAnswer` при провале гейта:
дублирует логику сторожа, тянет GitHub-чтения в горячий путь и не решает главный пробел
(proposed-ADR без вопроса вообще не всплывёт). Подъём бюджетов промптов — не требовался.

**Пересмотр.** Если появится третий репозиторий или имена ADR начнут совпадать между
репозиториями — дедупликацию перевести на составной ключ `repo/file` синхронно с
оракулами; до тех пор уникальность имён ADR в профиле — обязанность Координатора.

## D-040 · Маркер без dispatch_id/run_id — напоминание с точными ID, а не сразу пауза — 2026-11-05

Дата: 2026-11-05. Статус: принято Мастером («Делай все за один ход, что решил, и сразу
PR и мерж»). Инцидент: после D-039 доставка K-21 **прошла** (17:21:18, 6642 зн.),

попытки (dispatch_id / run_id). Карточка, ожидание и копия ответа сохранены локально;
попросите агента повторить маркер с ID этой выдачи». Работа сделана, но не зачтена.

**Контекст / кто виноват.** Виновник — **агент**: финальный маркер пришёл как
`CF_AGENT_RESULT: {"task":"K-21","scope":…,"check":0,"merged":true,"pr":…,"merge_sha":…,
"report":…,"logs":…}` — с двоеточием после имени, с `task` вместо `dispatch_id`/`run_id`
и без `status`. Транспорт **верно отказал** в подтверждении: совпадение только
карточки недостаточно, она могла быть перевыдана, и зачёт ответа без ID этой попытки
открыл бы подмену прошлой/чужой выдачей. Дефект транспорта — не в отказе, а в том, что
ветка mismatch сразу ушла в паузу, **минуя лестницу напоминаний**: случай «маркер есть,
но ID нет» не отличался от «ID чужие», и Мастер потребовался там, где хватило бы
авто-повтора маркера с точными ID.

**Решение.**
1. `dispatchIdState(result, expect)` классифицирует `match` / `missing` / `conflict`
   по тем же синонимам (`dispatch_id/dispatch/dispatchId`, `run_id/run/runId`).
   `missing` — ни один присутствующий ID не противоречит выдаче, но ID не хватает;
   `conflict` — хоть один присутствующий ID чужой/битый/противоречит.
2. `missing` → `markerMissing(role, expect, "CF_AGENT_RESULT", manual, "ids")`:
   существующая лестница (до `markerReminders=2`) шлёт `reminder.marker` с `why=ids`.
   Точные `dispatch_id`/`run_id` уже в промпте напоминания; агента просят повторить
   **только маркер**, работу не переделывать. Копия ответа сохраняется локально до
   классификации (`retainRejectedResult`), работа не теряется.
3. `conflict` → прежняя сразу-пауза `marker-mismatch` (возможен ответ прошлой выдачи).
4. **Проверка ID не ослаблена:** значения не подменяются (`adoptIds`), запись в Notion
   по неверному ID не идёт; после исчерпания напоминаний — пауза. Бюджеты **не подняты**
   (`reminder.marker` overhead ≤700, total ≤900).
5. Контракт → protocolVersion **1.9** (секция `d040`); ScriptCat **1.12.5**; Gateway 1.8.0
   и digest/REGULATION 1.5 не менялись. Docs `protocol.md`/`scriptcat-update.md`/
   acceptance-report согласованы.

**Проверка.** Новая регрессия `relay-marker-ids-reminder-integration`: `dispatchIdState`
на боевом маркере K-21 (`missing`), конфликт/битые/противоречащие синонимы (`conflict`),
короткие синонимы (`match`); пины маршрутизации `submitExecutor` и `reminder.marker`
`why=ids` в тотал-бюджете 900 с точными ID. `relay-review-dispatch-integration` обновлён:
«нет run/dispatch сдачи» → напоминание `ids`, чужие ID → пауза. Прогоны: `verify` —
**106 smoke / 18 regression / 2 tool-limit, exit 0**; `test:provision` — **28/28**;
`docs-smoke` OK. Тесты не ослаблялись: изменился только маршрут «ID нет» (пауза →
напоминание), маршрут «ID чужие» остался паузой.

**Отклонено.** Приём маркера без ID / подстановка ID из выдачи — сломало бы защиту от
зачёта чужой/прошлой попытки; напоминание при `conflict` — чужой ответ должен
останавливать цикл для разбора, а не переотправляться; подъём бюджетов — не требовался.

**Пересмотр.** Если агент снова шлёт маркер без ID после 2 напоминаний — пауза и Мастер
(как и прежде). Формат маркера в промпте (`marker.agent`) не менялся: требование
`dispatch_id`/`run_id`/`status` последней строкой остаётся обязательным.

   локальному снимку: восстановленное ожидание не стирается повторной уборкой.
4. Настоящий фантом без квитанции и без реплики этой выдачи по-прежнему возвращается в
   Ready. Чужой/прошлый run не принимается, чужая страница не читается как чат адресата,
   ID не подменяются. Намеренный отказ доставки (капча, ошибка Arena, повтор) гасит квитанцию; мёртвая реплика не доказывает доставку.
5. ScriptCat **1.12.9**; protocolVersion остаётся **1.10** (транспорт-внутренний фикс,
   аддитивная секция `d044`). Gateway 1.8.0 и digest/REGULATION 1.5 не менялись. Бюджеты
   промптов не поднимались, требования не обрезались.

**Проверка.** Новая проба `relay-delivery-receipt-smoke`: квитанция восстанавливает потерянный
`sentAt` без отката; чужой run и настоящий фантом снимаются; реплика этой выдачи в чате
адресата спасает ход, прошлый run и чужая страница — нет; живая очередь не снимается;

проверок. Прогоны: `verify` — **107 smoke / 21 regression / 2 tool-limit, exit 0**;
`test:provision` — **28/28**; `docs-smoke` OK.

**Отклонено.** Объявлять «не дошло» при наличии подтверждённой доставки/готового ответа;
править живую карточку K-30 вручную из песочницы; подменять dispatch/run ID; принимать

## D-045 · Записи хода доживают до перехода; потерянное ожидание восстанавливается сверкой — 2026-11-06

Дата: 2026-11-06. Статус: принято Мастером (действующее требование «правь Notion и Drive
самостоятельно, чтобы я просто продолжил работу»). Инцидент: SYN-1 · K-27 «Проверка
CLI-контракта», адресат Executor Core. Вопрос Мастера: «Проверь, почему цикл опять
остановился, хотя вроде сообщение было доставлено адресату Executor Core».

**Факты боя.** 09:29:03 — `budget_exceeded` (total 9096 > 7500) для исходной карточки;
Координатор разбил её на K-27 и K-32, лимиты не поднимались. 09:36:29 — план, turn
`638abf1e-4b48-43ab-a6c9-e548e6de0c19`. 09:36:54 — «Выдан ход»; журнал выдачи
`17H7pUziA1cG4l2i5vpMhMKEraomIM8iT` создан в 06:36:46.179Z и содержит единственный маркер
`CF_DISPATCH 40f6f0cf…:f74fd9d7…:task`. Строк перехода транспорта в журнале нет.
09:37:01 — убрана плашка. **09:37:12 — пауза `delivery-state-lost`** с сообщением
`01a1af93-3a0c-79ea-b456-263d4d41def7`: «Сообщение подтверждено в чате, но ожидание выдачи
потеряно». В 06:40:49Z Executor Core ответил полным отчётом с `CF_AGENT_RESULT` этой
выдачи (отчёт `1DVwxZyMoUaLajCeaxohsKP01Zd9rhRZI`: NOT PASS, verification-only, PR null,
O-1/O-2 PASS, O-3/O-6/O-7 FAIL по отсутствующему `res://cli/synapse.gd`). Ответ не принят,
карточка осталась Running. Доставка была, работа была, остановка ложная.

**Причина.** `GM_setValue` в ScriptCat синхронен только наполовину: значение сразу
кладётся в память вкладки, а запись в `ValueStore` уходит сообщением service worker'у —
и ничего не ждёт. `location.assign` сразу за пачкой записей обрывает её хвост. В
`sendToRole` очередь писалась **раньше** ожидания, поэтому усечение оставляло `K.pending`
без `K.expect`: очередь отправила задание, подтвердила его в чате и обнаружила, что
хозяина хода нет. Дополнительно `dispatchPromptInChat` искал только скобочную форму
«Задача … (dispatch …, run …)», которой в боевом промпте нет вовсе (компилятор печатает
«Карточка «…» · dispatch … · run …»): восстановление по реплике из D-044 было мертво
именно на реальном формате, а проба была зелёной на скобочной фикстуре.

**Решение.**
1. `flushBeforeNavigate(keys, ms = 4000)` перезаписывает ключи хода через `GM.setValue` и
   ждёт подтверждения. Ожидание ограничено `Promise.race` с таймаутом: подтверждение
   может не прийти вовсе (у вкладки нет слушателя значений), и зависнуть хуже, чем уйти.
   Отсутствующие ключи не создаются, отказ не бросается наружу, менеджер без
   `GM.setValue` получает паузу 150 мс. Барьер стоит перед **каждым** уходом со страницы:
   `sendToRole`, `navigateTo`, перечитывание страницы в цикле, перезагрузка после ошибки
   Arena, переход пилота.
2. `sendToRole` пишет `K.expect` **до** `K.pending`: при усечении теряется очередь, а не
   хозяин хода — такой ход разбирается штатной уборкой фантомов. Очередь несёт плоские
   опознавательные поля выдачи (kind/ref/runId/missionId/turnId/questionId/logId/title/url/
   sessionRepo/targetRepo/targetBranch).
3. `adoptOrphanDispatch` разбирает очередь без ожидания **до разбора просрочки** и до
   отправки, только для рабочих выдач: сверка карточки (Running, Run ID, Recipient Agent
   ID, Mission ID) → квитанция доставки или реплика в чате → очередь снимается и ответ
   читается без отправки; если реплики нет — ожидание восстанавливается и задание уходит
   ровно один раз. Порядок существен: K-27 пролежал бы в очереди часы, и прежний разбор
   просрочки снял бы доказанный ход как «остаток прошлой попытки». Вывод «реплики нет»
   делается только на отрисованной странице адресата; на чужой странице очередь
   сохраняется, а квитанция проверяется независимо от страницы. Расхождение с карточкой
   или недоступный Notion — пауза `orphan-dispatch` без отправки и без изменения карточки.
   План, приёмка и вопросы этим путём не идут.
4. `promptDispatchIds` — общий разбор боевой строки выдачи, формы продолжения
   «IDs прежние: dispatch_id=…, run_id=…», примера маркера и прежней скобочной формы.
   Он обслуживает и `sendKey`, и `dispatchPromptInChat`; ключ доставки остаётся
   подстрокой самого сообщения и меняется вместе с Run ID.
5. Квитанция доставки пишется и в ветке `delivery-state-lost` — **до** паузы. `resume`
   для этого вида больше не обещает повторную отправку подтверждённого сообщения.
6. ScriptCat **1.12.10**, добавлен `@grant GM.setValue`; protocolVersion остаётся **1.10**
   (аддитивная секция `d045`). Gateway 1.8.0 и digest/REGULATION 1.5 не менялись. Бюджеты
   промптов не поднимались, требования не обрезались.

**Проверка.** Новая регрессия `relay-handoff-flush-integration` работает на **настоящем
промпте боевого компилятора**, а не на фикстуре: скобочной формы в выдаче нет, разбор
находит ids, ключ доставки — подстрока сообщения и меняется с новым Run, напоминание и
продолжение опознаются; барьер ждёт подтверждение, ограничен таймаутом, не дублирует и не
создаёт ключи, не бросается при отказе хранилища; порядок «ожидание → очередь →
подтверждение → переход»; восстановленный ход не отправляется вторично, а при отсутствии
реплики уходит ровно один раз; пять видов расхождения с карточкой и отказ Notion дают
паузу без побочных эффектов; залежавшаяся шесть часов очередь с доказанной доставкой
снимается сверкой, а не как просроченная; с чужой страницы задание не уходит; проводка

## D-047 · План с замечаниями не переспрашивается (ScriptCat 1.12.12)

**Инцидент.** SYN-1, 06.11.2026. Мастер вернул миссию в 17:07:32, план с замечаниями ушёл в
17:07:57 (4385 б, turn `6b639dee-386a-4d27-bdf8-5d6383949276`). Координатор ответил к 17:18:
создал K-38…K-41 и дописал раздел «Возврат» в «Итог». В 17:19:30 журнал записал «Ожидание
Координатора началось до возврата миссии — это прошлый ход, а не ответ на замечания»,
ожидание сняли, и в 17:19:54 Координатору ушёл второй план подряд (4797 б, turn
`bd269b06-e5ed-407a-b55b-afcd62935085`): ещё 11 минут хода агента и расход лимитов. Дублей
карточек не появилось только потому, что второй ход перечитал очередь и правил K-39/K-40.

**Причина.** `returnEpoch` брал момент возврата как `last_edited_time` карточки миссии, а
`dropStalePlan` сравнивал с ним время отправки плана. Карточку правят и после возврата:
Координатор пишет «Итог» в том же ходе, поэтому отсчёт уезжал вперёд и живой план оказывался
«до возврата». Время правки карточки для этого вопроса непригодно по построению: правка
карточки и есть ответ на замечания.

**Решение.**
1. `requestPlan` кладёт в ожидание снимок `planBeforeReturn` — «план отправлен уже с
   замечаниями или до возврата». Решение принимается один раз, до отправки, и в карточку
   больше не переспрашивается; признак берётся из содержимого задачи (`returnBlock`
   непустой ⇔ в карточке есть «Замечания»), а не из отметки времени. Напоминание по тому же
   плану переносит снимок в новое ожидание — иначе повтор промпта терял бы признак.
2. `returnAnswered(mission)` — раздел «Возврат» в «Итоге» при непустых «Замечаниях». Это то же
   требование, которое `returnBlock` предъявляет плану, поэтому «раздел есть» и «этот ход
   получил замечания» — одно утверждение, а не догадка.
3. Строка журнала о возврате хранит момент объявления (`markedAt`) вместо `true`. Legacy-метка
   `true` остаётся объявленной, но времени не даёт.
4. `dropStalePlan` решает по порядку: снимок → раздел «Возврат» → `markedAt` → время. Правило
   по времени остаётся последним средством и снимает ожидания, начатые до первой отметки
   возврата: защита 24.10 (старый `done` не считается ответом на замечания) не отменена.
5. ScriptCat **1.12.12**; protocolVersion остаётся **1.11** (аддитивная секция `d047`) —
   форма маркеров, профили и блоки промптов не менялись. Gateway 1.8.0 и digest 1.5 не
   менялись, бюджеты не поднимались.

**Проверка.** `relay-return-epoch-smoke` дополнен тремя кейсами инцидента: (а) отсчёт впервые
считается уже после правки «Итога» — ход с замечаниями не снимается; (б) снимок плана сильнее
времени — `planBeforeReturn:false` держит ожидание, `true` снимает; (в) отметка объявления
возврата не снимает ход, начатый после неё. Проба проверена на падение: со снятой веткой
«Возврат» в «Итоге» она краснеет, а не проходит случайно; часы в новых кейсах выставлены на
момент шага, иначе проверка проходила бы по неверной причине. Прогоны: `verify` — **108 smoke /
22 regression / 2 tool-limit, exit 0**.

**Отклонено.** Поднимать бюджеты или число напоминаний; отменять снятие прошлого хода целиком
(вернуло бы 24.10); сравнивать планы по тексту промпта; считать ответ по времени правки
карточки; переспрашивать план «на всякий случай», если ответ на возврат уже пришёл.

**Пересмотр.** Если появится третий источник правок карточки миссии в том же ходе (например,
автоматическая запись «Круга»), признаки 1–3 всё равно остаются главными: они не зависят от
времени. Если же снимок `planBeforeReturn` начнёт теряться вместе с ожиданием, это повод
хранить его отдельным ключом хода, а не в `K.expect`.

## D-049 · Сцена модуля достижима: `provides.sceneEntries` связывает смысловой ID с ресурсом — 2026-11-06

Дата: 2026-11-06. Статус: принято Warden в пределах делегированных полномочий (техническое решение
внутри утверждённых границ, `docs/WARDEN.md` §1). Реализуется миссией SYN-2 (карточка S-1).
Обратимое: запись `docs/decisions/SYN-2.md` «неясно / решил / откат» оформляется исполнителем.

**Контекст.** Приёмка SYN-1 и внешний аудит независимо воспроизвели один и тот же разрыв: модуль с
валидным `provides.scenes` проходит `validate` и `resolve` (оба `ok: true`), после чего `run` отдаёт
`scene.id.unknown`, потому что `game/runtime/scene_registry.gd` — жёсткая карта из двух встроенных
сцен. Манифест не умеет связать смысловой ID с ресурсом сцены: в схеме `$defs.sceneId` прямо
запрещает путь к файлу. Итог: INV-3 (логика по смысловым ID) соблюдён, а путь автора из цели SYN-1
(«описать, проверить и запустить игру») не замкнут для собственной сцены автора.

**Решение.**
1. В манифест модуля добавляется **аддитивное** поле `provides.sceneEntries` — массив
   `{id, resource}`. `id` обязан входить в `provides.scenes`; `resource` — только `res://…tscn`,
   без `..` и абсолютных путей; запись проверяется на существование файла локально (без импорта
   движка и без сети).
2. Реестр сцен рантайма = базовая карта ядра + записи разрешённых модулей. `scene.id.unknown`
   перечисляет фактически доступные ID сборки. Один ID у двух модулей — ошибка `scene.duplicate`,
   а не «кто последний».
3. INV-3 не ослабляется: перечисления и логика по-прежнему используют смысловые ID; путь к ресурсу —
   представление, читается только реестром и никогда не попадает в правила. Тест `grep` по именам
   ассетов в правилах остаётся в силе.
4. `GameSpec` получает `entities` — определения с примитивными свойствами и без полей состояния
   экземпляра. Экземпляр создаётся рантаймом копией свойств, поэтому INV-4 проверяется в рантайме,
   а не только отсутствием полей в схеме (долг, найденный при приёмке SYN-1).

**Отклонено.** Хардкод сцен модулей в `scene_registry.gd` (повторяет исходный дефект); путь к сцене
непосредственно в `entry.scene` (нарушает INV-3 и размывает границу «данные против ассетов»);
необязательное поле без проверки существования файла (ошибка переезжает из `validate` в `run`).

**Проверка.** Оракул SYN-2 N-2…N-4: модульная сцена проходит validate/resolve/run; `expected` в
`scene.id.unknown` содержит модульные ID; четыре негативные декларации дают отдельные коды с
`path`/`expected`/`actual`, одинаковые на `en` и `ja`.

**Откат.** Удалить `sceneEntries` из схемы и примеров, вернуть сборку реестра только из базовой карты
ядра, убрать коды `scene.entry.unknown`, `scene.resource.missing`, `scene.duplicate` и их ключи в
каталогах. `entities` откатывается отдельно, удалением определений из схемы и рантайма.

## D-050 · Требование Node для автора: build-time зависимость до решения Мастера — 2026-11-06

Дата: 2026-11-06. Статус: **провизорное** решение Warden; граница продукта, окончательно решается
Мастером. Действует до явного решения Мастера или до отдельной записи о портировании.

**Контекст.** D-011 (2026-11-02) постановил, что отдельный Python/Node-рантайм в ядро не вводится, а
если он понадобится — это ADR. По факту `validate` и `resolve` выполняются процессами Node
(`game/validation/validator.mjs`, `game/modules/resolver.mjs`) через `OS.execute("node", …)`;
`package.json` требует `node >= 20.19.0`, `ajv` и `yaml` лежат в `vendor/` и в `NOTICE`, офлайн-установка
проверена. То есть автору, который ставит ядро, нужен второй язык, чего D-011 не предполагал.

**Решение (провизорное).**
1. Публичной точкой входа CLI остаётся Godot-скрипт (`res://cli/main.gd`); Node — исполнение двух
   шагов валидации и резолвинга, не второй CLI и не второй пользовательский интерфейс.
2. Требование `node >= 20.19.0` **явно документируется** для автора в `README.md` и `AGENTS.md`,
   с командой офлайн-установки из `vendor/`; скрытым требованием оно быть не должно.
3. Портирование валидатора и резолвера на GDScript в SYN-2 не входит; это отдельная миссия фазы 2
   с собственной записью, ссылающейся на D-011 и эту.

**Что здесь не решается.** Нужен ли автору Node вообще: (A) оставить как есть и документировать
(текущий дефолт), (B) бандлить Node в `tools/` рядом с Godot, (C) портировать валидатор и резолвер
на GDScript в фазе 2. Варианты A и C не меняют оракул; B добавляет в репозиторий второй бинарник и
влияет на размер и лицензии. Решает Мастер; до решения действует A.

**Проверка.** SYN-2 N-10 (README/AGENTS описывают требование Node) и N-8 (`cli.dependency.node_missing`
вместо сырого сбоя оболочки). SYN-P1 не запускается, пока требование не задокументировано: иначе
внешний автор упрётся в него на первом же прогоне.

**Откат.** Заменить пункт 2 на описание выбранного варианта B или C, сохранив пункт 1; при портировании
на GDScript запись закрывается ссылкой на новую, а D-011 снова действует без оговорок.

## D-052 · Пилотные роли: одноразовый `Pilot Author` и ведущий прогона `Pilot Host` — 2026-11-06

Дата: 2026-11-06. Статус: принято Warden; **пересматривает D-029 §2 и §6** (там было: пилотных ролей
не заводим, первую волну проводит Мастер вручную). Роли созданы в базе «Роли» со статусом `Ждёт`:
их активирует Мастер, добавив Agent URL. Обратимо: отключить роль, если волна не даст сигнала.

**Контекст.** Мастер: SYN-P1 будут выполнять одноразовые агенты, «для которых ролей сейчас нету».
Транспорт выдаёт работу только зарегистрированной роли по карточке, поэтому без строки в «Ролях»
прогон не выдать иначе как руками.

**Решение.**
1. **`Pilot Author`** (`Функция = Executor`, репозиторий `synapse`). Зона записи — только
   `pilots/<run-id>/**` (GameSpec, ассеты, сцена, `shot.png`, журнал). Ядро (`game/`, `cli/`,
   `schema/`, `examples/`, `docs/`) — чтение. Гейт — оракул SYN-P1 §3 на одном SHA, PNG открыт

## D-054 · Один знак в run_id — опечатка, а не чужой ответ (ScriptCat 1.12.15)

**Инцидент.** SYN-2 · S-4, 07.11.2026, 17:04:22. Executor Platform выполнил карточку
`4116f0cf-5705-8118-8349-c63d5524ed96` и сдал работу: отчёт
`Arena/synapse/artifacts/SYN-2-S-4-a437578a-report.md`, PR #26. В маркере `CF_AGENT_RESULT`
он написал `run_id` с одной заменой знака — `a437578a-e5db-4a26-b72d-41d2de180d6c`
вместо `a437578a-e5d6-4a26-b72d-41d2de180d6c`. `dispatch_id` совпал, в промпте
расхождения не было (там `e5d6` в единственном месте), то есть ID агент набирал по
памяти — и повторил ту же опечатку в трёх ответах подряд. Транспорт честно не принял
чужой, с его точки зрения, маркер и встал на паузу `marker-mismatch`. «Продолжить» её
не снимало: ожидание хранит прежний `runId`, и тот же маркер снова давал конфликт.

**Причина.** `dispatchIdState` возвращал `conflict` для любого валидного UUID, не равного
ожидаемому, — лестница `markerMissing(role, expect, "CF_AGENT_RESULT", manual, "ids")` не
запускалась. Классификация D-040 «ID выдачи нет» покрывала отсутствие ID, но не опечатку
в нём. Задуманная политика уже была описана: регрессия `relay-marker-ids-reminder-integration`
прямо говорит, что `marker-mismatch` — для «чужих/битых ID», а не для формата.

**Решение.**
1. `looksLikeTypo(value, expected)` в `22-executor.js`: оба значения — UUID, длина та же,
   различие ровно в одном знаке. `isUuid` отсекает битые значения и сдвиги строки
   (замена на дефис или с дефиса — не опечатка). Случайный v4 (`crypto.randomUUID()`)
   делает совпадение «всё, кроме одного знака» у двух независимых выдач событием с
   вероятностью 2⁻¹²³, поэтому порог «один знак» здесь строгий, а не мягкий.
2. `typoTiedToCard(role, expect, result)` — обязательное подтверждение из Notion: карточка
   несёт **ожидаемый** `Run ID` (его ставил сам скрипт) и того же владельца. Нечитаемая
   карточка (`checked: false`) подтверждением не считается.
3. Совпало — ответ принимается: копия присланного сохраняется (`kind: "dispatch-typo"`),
   в журнал идёт строка «Run ID с опечаткой (прислано … вместо …)», работа не повторяется,
   `run_id_typo` хранит присланное, а запись идёт по ожиданию. Не совпало — прежняя пауза
   `marker-mismatch` без изменений.
4. `marker.agent` (v4) и `reminder.marker`: «ID целиком из строки ниже» / «Скопируй ID из
   строки ниже». Раньше просьба звучала как «ID из промпта» — она не запрещала набирать
   UUID по памяти.

**Бюджеты не поднимались.** `reminder.marker` overhead остаётся 700 (было 725 при первой
редакции — формулировки укорочены, а не лимит поднят), `marker.agent` — 409; compact-повтор
всё ещё короче 900 знаков (`relay-arena-swallow-smoke`).

**Проверка.** Новая проба `relay-run-id-typo-smoke` на боевых ID: паузы нет, карточка

**Границы.** Это не разрешение «похожих» ID: два знака, другой UUID, чужая карточка,
отсутствие карточки — пауза. Присланный ID в Notion не подменяется, ожидание при паузе не
снимается, пауза снимается только человеком. Порог напоминаний и `markerReminders` не

**Что осталось за рамками.** Причины прочих пауз 07.11 независимы от этой: недоступный

## D-055 · Ход приёмки — не рабочая карточка: доставка доказывается по turn_id (ScriptCat 1.12.16)

**Инцидент.** SYN-2, 07.11.2026, 22:04–22:05. Ход приёмки миссии ушёл Warden, доставка
подтвердилась в чате, но отметки отправки в ожидании не осталось. Тик честно решил, что
это след упавшей попытки: «ожидание без отметки отправки — это прошлый ход» — снял
`K.expect`, открыл страницу адресата. Очередь `K.pending` с текстом приёмки осталась, и на
странице Warden `consumePending` упёрся в проверку, написанную для старой рабочей выдачи:
«Очередь адресована Reviewer. Проверьте чат и карточку: отправку не повторяю, очередь
сохранена». Цикл встал до Мастера, а Координатор после паузы не получил хода — карточка
S-7 осталась в `Submitted`.

**Причина.** `restoreMissingSendMark` умел доказывать доставку только по паре
`dispatch_id`/`run_id` (`dispatchPromptInChat`). У приёмки миссии, ответа на вопрос и
арбитража этих номеров нет — есть `turn_id`, напечатанный в самом задании. Поэтому живой
ход приёмки не мог быть доказан **никогда** и объявлялся фантомом при первом же разборе.
Дальше очередь попадала в три проверки (`17-arena-polls.js`), где видом хода считался
только `dispatch`, а всё остальное — «карточка, которую не отправляем»: «В очереди осталась
рабочая карточка Reviewer», «Очередь адресована Reviewer», «Адресат рабочей очереди не
найден среди активных Executor/Auditor». Для карточки они верны (D-040, D-042), для хода
приёмки — ложны: ни карточки, ни `Run ID` у такого хода нет, а адресат по уставу — роль с
функцией Reviewer.

**Решение.**
1. `REVIEW_TURN_KINDS` = `review`, `answer`, `arbiter`. Вид хода ставит `sendToRole` в
   ожидание (`kind`), и пока ожидание живо, верить надо ему: роль могли перевести из
   Executor в Reviewer уже после постановки в очередь.
2. `reviewTurnInChat(expect)` — доказательство доставки хода приёмки: своя реплика в чате
   **адресата** с его `turn_id` (обе формы — `turn_id: <id>` и `"turn_id":"<id>"`). Запреты
   те же, что у карточки: капча, `deadSend`, чужая страница. `restoreMissingSendMark`
   проверяет оба вида хода.
3. В `consumePending` введён `reviewQueue`: вид хода из живого ожидания либо — если
   ожидание уже снято — маркер `CF_REVIEW_RESULT`/`CF_ANSWER_RESULT`/`CF_ARBITER_RESULT` в
   тексте очереди. Три проверки «Reviewer» выполняются только вне `reviewQueue`.
4. Добавлен `adoptOrphanReview` — сверка осиротевшей очереди хода приёмки по `turn_id`.
   Доставка доказана — очередь снимается, ответ читается, второй отправки нет. Не доказана —
   ожидание восстанавливается с `missionId`/`turnId`/`questionId`/`kind` и ход уходит ровно
   один раз обычным путём. `turn_id` не читается — пауза `orphan-review` с точной причиной.

**Границы.** Рабочая карточка, ошибочно адресованная роли с функцией Reviewer, по-прежнему
блокируется паузой `reviewer-task-pending` и карточку не трогает. Нераспознанная очередь без
ожидания сохраняет прежнее осторожное поведение. Откат карточки в Ready у хода приёмки не
выполняется: откатывать нечего. Бюджеты промптов, `markerReminders`, тексты `marker.agent`
и `reminder.marker` не менялись; `protocolVersion` 1.11 (секция аддитивная), Gateway 1.8.0 и
digest 1.5 те же.

**Проверка.** Проба `relay-review-turn-orphan-smoke` на настоящих блоках `relay.user.js` и
настоящих промптах компилятора (`review`, `answer`): доказательство по `turn_id`; отказ от
доказательства при чужом `turn_id`, чужой странице, капче и `deadSend`; живой ход приёмки не
снимается как фантом; очередь приёмки не выдаёт паузу «адресована Reviewer»; осиротевшая
очередь восстанавливается сверкой без второй отправки, а без читаемого `turn_id` — пауза
`orphan-review`; рабочая карточка Reviewer блокируется как прежде. Мутации (шесть: убрать
сверку по `turn_id`, снять обход паузы, вернуть ход приёмки в сторож рабочей карточки, убрать
вызов сверки, сверять чат на чужой странице, не сверять сам номер) — каждая роняет пробу.

   `relay = "binding"`. Пауза теперь называет причину («мешает привязка карточек»), а не
   «запись в Notion», и говорит, что карточки не скрываются и не меняются.
3. `tasks(state, mission, { allowUnbound })`: карточка этой миссии без UUID по-прежнему
   останавливает **выбор очереди**; карточка другой миссии в очередь не попадает и паузы не
   даёт — о ней одна строка в журнале со ссылкой на «Проверить Mission ID карточек».
4. `queueOf(mission, { strict })` зовёт страж только в строгом режиме (выбор очереди). Мягкое
   чтение отдаёт непривязанные свои карточки в `queue.unbound`. Строгий режим — ход
   Координатора; мягкий — приём ответа, возврат миссии, вопросы Мастера, подсчёт для `done`.
5. Приёмка миссии перед закрытием спрашивает привязки отдельно (`missionBindingBlockers`,
   потому что `Accepted` очередь не читает) и встаёт на паузу `review-unbound`. Ветка `rework`
   привязкой не блокируется: замечания уже получены, их надо записать.

**Границы.** Карточки не скрываются и не меняются; непривязанные не выдаются — выдача
по-прежнему требует `Mission ID`. Статусы `Submitted`/`Accepted`/`Rework` ставит Координатор.
Оракул, бюджеты промптов, профили и `protocolVersion` 1.11 не менялись (секция `d056`
аддитивная). Рабочие карточки Reviewer не отправляются.

**Проверка.** Проба `relay-unbound-binding-smoke` на настоящих функциях бандла: чужая
непривязанная карточка не валит шаг и не попадает в очередь; своя непривязанная видна и
останавливает выбор очереди; мягкое чтение называет свои карточки в `queue.unbound`, строгое
валит шаг; карточка в `Accepted` без привязки мешает закрытию миссии; пауза `review-unbound`
стоит до закрытия и не стоит в ветке `rework`. Мутации (шесть: страж валит любую карточку,
`queueOf` всегда строгий, нет паузы `review-unbound`, `tasks` игнорирует `allowUnbound`,
`cardNamesMission` никого не узнаёт, очередь не отдаёт `unbound`) — каждая роняет пробу.

**Мастеру.** S-13…S-16 нужно привязать (`Mission ID` = миссия SYN-2 и «Миссия» = её имя) или
перевыдать планом: скрипт их не трогает и статусы им не ставит.

## D-057 · Фаза 1 принята с ограниченной областью инвариантов — 2026-11-02

**Решение.** SYN-2 принимается (`accept`, круг 1, `6cff12a`), фаза 1 считается закрытой
функционально, но **не** объявляется «инварианты защищены». INV-12 считается подтверждённым для
арены и объявленного набора входов, INV-13 — для имеющегося кода и литералов, которые ловит текущий
анализатор. Универсальных утверждений о них в отчётах и документации не пишем. Перевод фазы 1 в
«защищено» — миссия SYN-3; фаза 2 не начинается до её приёмки.

**Причина.** Аудит и приёмка одинаково показали: отпечаток мира не зависит от локали (нет текста,
кадра, локали), анализатор литералов обходится многострочным литералом и конкатенацией. Зелёная
приёмка в таком виде неотличима от регрессии, и любая следующая миссия опиралась бы на доверие
без измерения.

**Отклонено.** Признать SYN-2 `rework` (оракул пройден, дефекты — не в пунктах оракула, а в их
доказательной силе); ослабить формулировки приёмки (запрещено правилами миссии); починить «заодно»
в рамках фазы 1 без отдельной миссии (нет признака «сделано», нет очереди, нет приёмки).

**Проверка.** `docs/handoff/phase-1-warden-decision.md` §A, F-1…F-9; SYN-2 §5 N-1…N-10 пройдены
на `/tmp/syn-r1` @ `6cff12a`.

**Пересмотр.** При приёмке SYN-3 — область действия инвариантов переписывается по факту измерения.

## D-058 · Отпечаток мира v2: равенство значит только перечисленное — 2026-11-02

**Решение.** `synapse.world-state.v2` — снимок наблюдаемого: `locale`, `frame`, `text`,
`tooltip_text`, `title`, `visible`, геометрия, плюс обязательное поле `fingerprintScope` со списком
включённых полей. Сравнение отпечатков допустимо только внутри одной версии. `v1` остаётся
читаемым (исторические артефакты) и в доказательствах не участвует. Порядок нормализации,
перечень полей и смысл `fingerprintScope` пишет `Contract Architect` (B1), принимает Warden,
соответствие проверяет `Spec Auditor`.

**Причина.** v1 равнялся у прогонов, чьи картинки различались на 4100 пикселей: два инварианта
(INV-12 и запрет пользовательских строк вне каталогов) «доказывались» равенством величин, которых
эти строки не касаются.

**Отклонено.** v1 + отдельный `--snapshot` (два источника истины, доказательство зависит от того,
какой файл открыли); хеширование всего дерева сцены без перечня полей (нельзя сказать, что именно
доказано, и любое косметическое изменение ломает сравнение).

**Проверка.** `en`/`de` на 120 кадрах дают разные отпечатки; `en` дважды подряд — побайтово равные.

**Пересмотр.** Если синхронный снимок станет дорогим по времени на 8 локалях (C3).

## D-059 · Проверка литералов — fail-closed на настоящем парсере — 2026-11-02

**Решение.** `i18n-no-literals` разбирает GDScript настоящим парсером (`gdtoolkit`/`gdparse`) в
изолированном venv вне `package.json` и вне рантайма ядра; самописный токенизатор допускается только
как быстрый предфильтр и не может выдать «0 находок». Недоступен парсер — проверка завершается
кодом ≠ 0 с машинной записью. Простые литералы продолжают ловиться.

**Причина.** Самописный токенизатор пропускал `"""…"""` и `String.chr(72) + "…"` (проверено:
`scanned=1 user-facing-literals=0`, код 0), то есть INV-13 обходился тремя строками.

**Отклонено.** Только регулярные выражения (не различают строку и комментарий надёжно);
отказ от проверки в пользу ревью (не автоматизируется); перенос проверки в GDScript (нет парсера
без движка).

**Проверка.** Четыре пробы (`multiline`, `concat`, `chr`, `plain`) — все четыре код ≠ 0; без парсера —
код ≠ 0.

**Пересмотр.** Если `gdtoolkit` перестанет ставиться из доступного реестра — B5 падает, а не
пропускает; замена парсера — новая запись.

## D-060 · Код ошибки называет причину; подмена класса отказа запрещена — 2026-11-02

**Решение.** `runtime.engine.missing` возвращается только когда движка нет. Ошибка записи состояния —
`cli.run.state.write_failed`, отсутствующий файл действий — `actions.file.missing`. `params.path`
равен пути, который передал автор. Вложенный процесс собирает argv так, что значения с дефисами и
пробелами не склеиваются. Любой новый код — через карточку контракта и запись в реестре.

**Причина.** `run --state /proc/nope/state.json` возвращал `runtime.engine.missing` с
`params.path = "/--state"`, то есть пользователю предлагалось установить движок вместо исправления
пути; INV-14 (диагностика не зависит от среды) нарушался.

**Отклонено.** Один «общий» код на любой отказ вложенного процесса (диагностика перестаёт различать
причины); передача argv строкой с экранированием (источник искажений).

**Проверка.** V-4: три разных кода на три разных отказа, `params.path` = переданный путь.

**Пересмотр.** При появлении вложенных процессов других типов (сборка, экспорт).

## D-061 · Игровой контент — все восемь локалей — 2026-11-02

**Решение.** К концу SYN-3 игровой UI арены переведён на все восемь локалей
(`en`, `ru`, `zh-Hans`, `ja`, `pt-BR`, `de`, `fr`, `ko`), порог `i18n-check` для ключей `game.*` —
100 %. До приёмки C1 действует порог SYN-2 (≥ 95 %). Набор локалей не урезается.

**Причина.** Восемь локалей в каталогах и три в контенте означали, что автор видит непереведённый
интерфейс на пяти языках; для платформы, где язык автора — не английский, это видимый дефект.

**Отклонено.** Оставить три локали в контенте до фазы 2 (переносится тот же разрыв);
машинный перевод без ревью (проверять нечем, тофу и обрезанный текст не ловятся).

**Проверка.** C1: восемь PNG открыты, тофу нет, `i18n-check` 8×N с 100 % для `game.*`.

**Пересмотр.** При добавлении новых игровых сцен — порог остаётся, набор ключей растёт.
